- A `Locale` value and a selection chain (flag, saved preference, OS language, English), with a per-message fallback to English (5.1).
- A `language` field in `gallery.json` (5.1).
- A live switch of the language, without restart, built in phase 4 (5.4, decided 2026-11-14).
- One number formatter in `pg-client`, and Qt's standard buttons replaced by Words (5.3, 5.7).

**Open** (owner only): the minimum window width, once it is measured in phase 1 (3.7). The reviewer for each later locale is named when that locale is added (5.9).

## Goals and non-goals

The goal is that a user can see the window, the notices, the status and toast lines, the command line's own lines and the frames of the crash and error boxes in a chosen language, with the panic text and the technical detail kept as recorded (5.5, 5.6). English stays the source and the fallback: a translation that is missing or broken shows English text, never a Fluent id or a braced placeholder. The app keeps one engine for Rust and QML text and one set of `.ftl` files, so that the browser client and the desktop read the same words. Identifiers, notice codes, paths, file names and user data keep their exact values in every language. The product name is fixed as "Photo Gallery" in every locale (3.5). The language is chosen per machine, and a change applies at once (5.4).

The non-goals for the first translated release are: translating the developer documentation (only the site is translated, after the second locale, 3.5), translating log messages, translating clap's help output (the CLI stays English, 3.5), right-to-left layout (5.7), localised dates (5.3), bundling a font, and translating text that the operating system or a third-party tool produces (5.6).

## Current state

### 3.1 The seam

- The English words are three Fluent files compiled in with `include_str!`: `crates/client/locales/en/text.ftl`, `ui.ftl` and `cli.ftl` (`crates/client/src/text/words.rs:10-16`). They hold 209, 155 and 41 entries respectively, counted by line in the working tree (the 41 cli.ftl entries equal the 41 Line variants, which the id test in cli.rs pins).
- The bundle is one `thread_local!` built from those files on first use per thread (`words.rs:18-21`, `english()` at `words.rs:31-46`). The language tag is the literal `"en"` (`words.rs:33`).
- `set_use_isolating(false)` is called (`words.rs:36`) so that placeables are not wrapped in bidi isolation marks. The comment says the screen wants plain text.
- `add_builtins()` registers Fluent's builtins (`words.rs:38`). The comment on that line mentions `NUMBER()` and `DATETIME()`, but only `NUMBER` is registered in fluent-bundle 0.16, and `DATETIME` is a TODO there (per the investigators, `fluent-bundle-0.16.0/src/bundle.rs:599-603`). The comment is wrong, and it is corrected in phase 0.
- The parse of each file keeps what parsed (`FluentResource::try_new`'s partial resource) and `add_resource`'s result is checked by `debug_assert!`, so a debug build or a test stops on a syntax error or a repeated id in the compiled-in English; a release build shows the rest of the file. (Before this change both results were discarded, and a syntax error dropped entries silently, so their lines showed as ids).
- `shown(id, args)` (`words.rs:60-68`) returns the id when there is no entry or no value, and it discards the resolver's error list (`words.rs:64-65`). A missing variable is written as a braced name and the error is not read.
- The pseudo-locale is a process-wide `AtomicBool` set by `set_pseudo` (`words.rs:23-28`), read in `shown` (`words.rs:67`), and applied to the whole line after formatting (`pseudo()` at `words.rs:72-89`; ASCII letters accented, padded by a third plus one, bracketed in U+27E6 and U+27E7).
- `ui(id, count, text, other)` (`words.rs:51-57`) is the entry point for the QML words; `count` chooses a plural form and `text` and `other` are shown as given.
- The Rust `Message` enum has about 101 variants (`crates/client/src/text/message.rs:58-113` macro, `115-255` variants), each mapped to a Fluent id and to named arguments (`message.rs:85-93`). The CLI's `Line` enum has 39 variants at HEAD and 41 in the working tree (`crates/client/src/text/cli.rs:19-22`); `line()` is at `432-438` at HEAD and `447-453` in the working tree.
- Notice ids come from one `ids!` table in pg-model (`crates/model/src/notice.rs:798-848`; the `title_id` and `body_id` methods it generates start at `:782`) and are looked up as `notice-<code>-title`, `notice-<code>-body` and `source-<code>` (`crates/client/src/text/notice.rs:43-60`).
- `RefusedReason` codes are kebab-case (`crates/model/src/refusal.rs:58-84`), and their words come from the seam (`crates/client/src/text/message.rs:262-270`).
- Command-line `--locale` accepts only `pseudo`, and the parser rejects any other value (`crates/desktop/src/command_line.rs:271-273`, tests at `:646-700` treat `--locale=fr` as a bad option). `set_pseudo` is called once at startup (`crates/desktop/src/lib.rs:129-130`).
- No system locale is read anywhere in `crates/` (no `GetUserDefaultLocaleName`, `QLocale::system`, `LANG` or `LC_ALL` read). The `windows` crate lacks `Win32_Globalization` in the workspace features (the `windows` entry in `[workspace.dependencies]`), and `cxx-qt-lib` 0.10 has no `QLocale` wrapper (per the locale investigation).

### 3.2 The QML

The count of such calls is 141 in one investigation and 119 in three others (see 3.10).

### 3.3 Number and date formatting

- Seven QML sites format numbers or dates with the process default locale: seven `Qt.locale()` calls on six lines (`TopBar.qml:85-86`, `GalleryGrid.qml:151-152`, `FolderTree.qml:63`, `FilterBar.qml:62`), and one `Qt.formatDateTime` with the fixed pattern `yyyy-MM-dd hh:mm` (`InboxPanel.qml:326`, which is not a `Qt.locale()` call). No `QLocale` default is set anywhere, so these follow the Windows user locale.
- Rust groups counts with a fixed comma (`crates/client/src/text.rs:247-251`, `group_digits` around `:264-279`), formats the info line's MB and KB with `{:.1}` and `{:.0}` (`text.rs:220-222`), and uses a fixed point in the CLI (`crates/cli/src/lib.rs:95-96, 411` and `report.rs:107-109`). The pieces of one window can therefore show `1 234` from Qt and `1,234` from Rust.
- Fluent's `NUMBER()` in fluent-bundle 0.16 does not localise grouping or the decimal mark. `FluentNumber::as_string` is Rust's `f64` to-string with minimum fraction digits, `use_grouping` is parsed and never read, and the locale is used only for plural rules (per the locale investigation, `fluent-bundle-0.16.0/src/types/number.rs`). `message.rs:28` says a locale formats a range's end (`NUMBER()`), which is false for this version; `words.rs:37` names `NUMBER()` and `DATETIME()` without that claim, and `text.rs:95-98` says only that range ends are Fluent numbers.
- Dates: `DATETIME` is not registered. The filter line's dates use `Day`'s `Display`, which is always `yyyy-mm-dd` (`crates/model/src/date.rs:82-86`, `crates/client/src/input.rs:110-112`, `text.rs:104`).
- Only the plural selector gets a count. Fluent lines therefore show `1234` ungrouped, because a count is a number and a text value is shown as given, while Rust pass lines show `1,234` (`crates/client/src/text/message.rs:42-53`, `text.ftl:80-82`).

### 3.7 Qt's own strings, fonts, mirroring and right-to-left

- Qt's translator is not installed: nothing calls `QTranslator`, `installTranslator`, `QLocale::setDefault`, `retranslate` or `LanguageChange` in `crates/desktop/src`, `cpp`, `qml` or `crates/client`.

### 3.9 Does the Fluent decision still hold

The 2026-11-06 design record recorded two reasons for Fluent over Qt's `.ts` (its line 56, not in git; the 2026-11-12 rewrite dropped them): the same `.ftl` serves Rust and a JavaScript client, and Qt's tooling would not reach a non-Qt web client. The first reason is conditional on the web stack, which `WEB_CLIENT.md` does not yet choose (3.10). The second is the same argument in other words. Both reasons rest on the web client, and the web verdict is now the shared QML app, so neither reason decides the desktop question on its own.

The desktop argument stands on other facts. Most of the app's user text is built in Rust (about 101 messages, 39 CLI lines and 47 notice kinds), and `lupdate` extracts strings from C++ and QML sources, not from Rust `format!` calls (an inference from Qt's tool design, not verified in this study). A Qt-only route would therefore need a second extraction path for the seam, which is what Fluent already provides. The seam is also already wasm32-clean (`tools/lint.py:21`), and the S7 pass (`REFACTOR_DESIGN.md:102` in the 2026-11-06 record, "check passes; plurals work; licences allowed") is confirmed for the check and the licences, but not for plurals, because no test runs a plural.

Two measured gaps count against relying on Fluent alone. `NUMBER()` does not localise grouping or the decimal mark in 0.16, and `DATETIME` is not registered (3.3). So number and date formatting is a separate design item (5.3), whatever engine holds the words. Fluent's isolation default is off in this code (`words.rs:36`), which is a right-to-left blocker to be revisited (5.7). Neither gap is a reason to change engine; both are reasons for a formatter and a direction design beside it.

## Design

### 5.1 Locale model

The design adds a `Locale` value to `pg_client::text`. It holds a `unic_langid::LanguageIdentifier` and nothing else, and it replaces the process-wide pseudo flag as the thing that selects a bundle. The pseudo-locale stays a separate switch, as it is now, and wraps whichever bundle is chosen, so that pseudo can be combined with a real tag later, which needs its own flag (for example `--pseudo`).

The English bundle is always built, because it is the fallback. A chosen locale adds its own three resources and falls back per message. The resource list is a single table in `words.rs`:

```rust
// crates/client/src/text/words.rs (proposed shape)
const LOCALES: &[(&str, [&str; 3])] = &[
    ("en", [
        include_str!("../../locales/en/text.ftl"),
        include_str!("../../locales/en/ui.ftl"),
        include_str!("../../locales/en/cli.ftl"),
    ]),
    // ("de", [include_str!(...), include_str!(...), include_str!(...)]),
];
```

Each locale is a compile-time embedding, which needs no file read at run time. That fits the `clippy.toml` ban on std file reads in `pg-client` (per the investigation), works in WASM, and lets one cargo test iterate the table without reading the disk (5.9).

The selection order is the one the investigation recommends (LR-04), with two points that this document adds:

1. An explicit `--locale=<tag>` on the desktop and the CLI. This is a real option, which replaces the pseudo-only parser at `command_line.rs:271-273`. The CLI has no locale option and no `set_pseudo` call today (its flags are in `crates/cli/src/args.rs`). It resolves its folders through `cli.layout()` (`args.rs:25-26`) but never reads `gallery.json`, so the CLI needs its own `--locale` in `args.rs`, its own step 2 read from `cli.layout()`, and its own call of `set_pseudo` for phase 3. An explicit unsupported tag is shown on a named surface (a status-line Message on the desktop, stderr on the CLI). The existing bad-option path only logs it, so this needs a new surface.
2. The `language` value in `gallery.json`, an optional BCP 47 tag, read through `Prefs` (`crates/app/src/prefs.rs:18-41`). It is `None` for "use the system language". Old files read it as `None`, because the struct is `serde(default)`.
3. The Windows display language, read once at startup with `GetUserPreferredUILanguages` (the `windows` crate needs `Win32_Globalization` added to the features in its `[workspace.dependencies]` entry). `GetUserDefaultLocaleName` is not the call for this, because it returns the regional-format locale, which can differ from the display language. The Qt side has the same distinction: `QLocale::system()` is the format locale, and `QLocale::uiLanguages()` is the display list, which would be the alternative if the Rust side should not read it. The Rust read is proposed. Its rule for choosing from the list (decided 2026-11-14): walk the list in its order, take the first tag that exactly matches a `LOCALES` entry, else the first whose primary language matches one, else English.
4. English.

A tag that is not in `LOCALES` is skipped at steps 2 and 3, and the next step is used. Only an explicit flag at step 1 is an error. Step 1 (the flag) and step 3 (the Windows language) can run where `set_pseudo` is called now (`crates/desktop/src/lib.rs:129-130`). Step 2 cannot: the saved `language` is in `gallery.json` under `config.layout.prefs()`, `Config::from_env` resolves the folders only at `lib.rs:137-140`, and the prefs store is opened inside `app::open` (`crates/app/src/app.rs:78`, called at `lib.rs:164`). The chain is therefore resolved after `Config::from_env` and after `pg_log::init` (`lib.rs:142`, so the once-only fallback log line is kept), and before any line is worded. That step needs a read of `gallery.json` that does not open the whole prefs store. The data-folder error at `lib.rs:139` uses steps 1 and 3 and English, as decided in 5.1.

There is a start-up circularity to settle. The preferences file lives under `PG_HOME`, which the data-folder layout resolves (`crates/app/src/config.rs:13-23`), and the data-folder errors happen before the file can be read (3.5). Those errors cannot use step 2. The decided rule (2026-11-14) is that they use step 3 when it exists and English otherwise. This is the most proper option: it uses the user's own ranked language list, needs no second store, and does not discard the user's language. The same startup function resolves the chain at both points. Before `gallery.json` is read, it uses the OS list alone. Once the saved `language` is read, that choice takes over.

The fallback is per message, and it is implemented in `shown(id, args)`. The chosen bundle is tried first. If it has no entry, no pattern, or formatting raises any resolver error, the English bundle formats the same entry with the same arguments. The fallback is logged once through `pg_log` in English, since logs are English (5.6). Fluent does not provide a bundle-level chain (fluent-bundle 0.16 `bundle.rs:134-137, 374-380, 402-404`), so the app builds it here. A translated entry that names a term or message existing only in English raises a resolver error, so the rule above shows English for it at run time. Check 5 in 5.9 reports it at build time.

The language is stored in `gallery.json` under a new `language` key. It is per machine (decided 2026-11-14); the catalog and an environment variable were the rejected alternatives. It is a per-device choice, following the preference-scope row at `WEB_CLIENT.md:558` (decided 2026-11-14), not a per-library one, which is why it does not belong in the catalog. The settings bridge (`crates/desktop/src/settings.rs`) already reads and writes prefs through `update`. **Settings control (designed 2026-11-14).** One row in that settings screen, and in the web settings page: "System", then each locale in its own name, and the change applies at once (the live switch, 5.4). Phase 4 builds it.

### 5.2 Messages

**The Rust side.** Every user-visible Rust string is a `Message` (`crates/client/src/text/message.rs`), a `Line` in the CLI (`cli.rs`), a notice (`pg_model::Notice`, worded by `crates/client/src/text/notice.rs`), or a `RefusedReason` word (`crates/client/src/text/message.rs:263-270`, `refused_reason`). Each has a Fluent id (`Message::id`, the `messages!` macro at `message.rs:58-113`) and named arguments (`Message::args`, `message.rs:85-93`). The id test at `message.rs:285-309` fails when an id is missing or duplicated. Adding a variant needs an entry in `text.ftl` and the compiler's exhaustive match, and that is already enforced.

**The QML side.** A QML label is `words.text("ui-...", ...)` or `words.phrase(...)` with a literal id and entries in `ui.ftl`. The facade is `crates/desktop/src/words.rs:13-35` and its bridge `words_bridge.rs:23-39`. The desktop test (`words.rs:39-79`) fails when a QML id is missing from `ui.ftl` or an entry is unused. The test does not see dynamic ids, and it does not see ids that pass through a variable (none exist today).

**The CLI.** A CLI line is a `Line` (`cli.rs:19-22`) worded from `cli.ftl`. Help text is not in the seam, and it stays English (decided 2026-11-14).

**The rule for any new string.** A new string that a user reads is added in the same change as its id, and it is written as an entry, never as a Rust literal in `format!`, a QML literal, or a concatenation. The rule has five parts.

1. A string a user reads is an entry in one of the three files, reached through a `Message`, a `Line`, a notice kind, or a `words.text` or `words.phrase` call.
2. A value that is data (a path, a name, a number, a code) is passed as an argument. The English entry places it, and the translation does too.
3. A log line or a diagnostic is English and is not an entry. A string a user should read is never sent to the log instead of an entry.
4. A symbol may stay literal in QML only when it is the same in every locale. The rating glyphs are Rust constants (`text.rs:29`) and move to a symbol table if a locale differs.
5. A new id is added to every locale file in the same change. A locale that lacks it shows English through the fallback, and the checker reports the gap as untranslated, not as an error.

**The moves this design requires.** The following are hard-coded English that the rule would move, in rough order of value. Also needed: the CLI's `Debug` list (`crates/cli/src/dups.rs:56`, still a `Debug` format at HEAD, confirmed; it becomes a `Line` variant in phase 1), the damage display (`crates/dbfile/src/judge.rs:46-53`), the picker messages (`crates/platform/src/picker.rs:86, 107`: `:86` is a diagnostic and stays English, and `:107` is behind the `NATIVE` guard at `crates/desktop/src/picker.rs:81`, so no user reaches it), the crop refusals (`crates/edit/src/crop.rs:21-27`, which reach the user as `CropFailed` through `pg_crop::save`), and the codec bail (`crates/codec/src/animation.rs:36`, which its caller never shows, so it stays English), and the "damaged BMP" bails (`crates/edit/src/rewrite/bmp.rs:14, 19, 40`), which reach the crop and rotate failure notices (`crop.rs:56`, `rotate.rs:76`) and so become typed refusals in phase 5 and `controller.rs:42-46`. None is in a phase. The keys hint is already entries in the working tree: its 22 labels are `ui-hint-*` entries and its separator is `ui-hint-separator` (`keys.rs:204-230`, `text.rs:315-318`, `ui.ftl:182`), so the pseudo-locale reaches it (QQ-01 is closed there). What remains is the `Hint` naming and the English pins of the key tests. The command-line refusals (`command_line.rs`, about 20 sites) become `Message` variants. The caption (`alert.rs:5-6`) uses `ui-app-name` through the seam. The fatal and data-folder messages (`lib.rs:122-123, 139`, `dirs.rs:33, 41`) become typed errors with seam text. The CLI borders contexts (`borders.rs`) become `Line` variants. The CLI's `main.rs:31, 50` and `lib.rs:146, 167, 301, 344` become `Line` variants. The value-parser messages (`args.rs:137-147`) become clap value-parser errors built from words. The QML concatenations (3.2) become entries with values. The `E`, `W`, `I` log letters become entries.

### 5.3 Plurals, numbers, dates and sentences built from parts

**Plurals.** Fluent selects on `$count` with the CLDR rules that `intl_pluralrules` supplies for the bundle's language identifier (LR-09: all 73 candidate languages are present, and an unlisted language falls back to English rules). The English files use only `one` and `other` (`ui.ftl:165-167`, `text.ftl:80-86`). A Polish, Russian or Arabic file needs more variants, and each translated select keeps `*[other]`. The checker (5.9) verifies that every select in a translation has a default, and that the selector values the Rust side sends are covered.

**Numbers.** There is no single formatter. QML uses the OS locale through `Qt.locale()` (seven calls on six lines), Rust uses fixed separators (3.3), and Fluent's `NUMBER()` does not localise in 0.16. The proposal is one formatter in `pg-client`, `Numbers`, with the grouping separator, the decimal mark and the minimum fraction digits for each locale in the `LOCALES` table. A hand-kept table of separators is the smallest option and works in WASM. A number-formatting crate, such as ICU4X's decimal formatter, is the more complete option; it was not checked for licence, size or `wasm32` support in this study, and no ICU or number-formatting crate is in the tree (LR-15). Decided: the hand-kept table is used, and ICU4X is revisited only for a locale whose number patterns go beyond separators. Both sides then use the formatter: `group_digits` (`text.rs:264-279`), the info line (`text.rs:218-223`), the CLI's `{:.2}` (`cli/lib.rs:95-96`), and the QML sites, which take the formatted string from Rust or call `Qt.locale` with the same locale set by `QLocale::setDefault` at start-up (through C++ glue, since `cxx-qt-lib` has no `QLocale`). The source is the app's chosen locale, with the system's as fallback (decided 2026-11-14), and one formatter serves the desktop and the browser build.

**Counts as text.** A count shown to the user is formatted by the `Numbers` formatter and passed as a text value, and the `count` argument is used only to pick the plural form. That removes the two forms in LR-08. Range ends that Fluent formats are passed as numbers and formatted by Fluent, which is English-only until the formatter is wired in, so those ends are moved to text as well.

**Dates.** Decided: ISO `YYYY-MM-DD` on every surface in this release, and localised dates are a non-goal. The proposal for the first translated release is to keep ISO `YYYY-MM-DD` as a fixed, non-translated format, because the filter's parser accepts only that shape (`crates/model/src/date.rs:64-70`, `crates/client/src/input.rs:99-112`, SF-06). The placeholder `ui-date-format` then stays the fixed shape and is shown as a hint, not as a translated phrase. A localised date display (the inbox's `yyyy-MM-dd hh:mm` pattern at `InboxPanel.qml:326`, and the `Day` display at `date.rs:82-86`) needs a locale-aware parser first, and no phase in section 6 builds it. Phase 2's `QLocale::setDefault` can change the locale Qt uses for `Qt.formatDateTime` (`InboxPanel.qml:326`), so that call is pinned to a fixed locale in phase 1 (decided 2026-11-14). The screenshot matrix checks that nothing visible changes.

**Sentences from parts.** A sentence is an entry with variables, never a join. The joins to remove are: the info line (`Hud.qml:58, 89-96`), the counter (`Hud.qml`), the group title (`InboxPanel.qml`), the borders join (`text.rs:195`), and the hint and selection lines, which are entries already in the working tree (`text::hint` at `text.rs:315-318` joins `ui-hint-*` entries with `ui-hint-separator`; the selection line is `ui-selection-line` at `ui.ftl:206`, with its three-space gap now inside the entry). The describe() separators at `text.rs:100` and `:153` were not re-checked. Structure (a newline, a fixed indent) may stay in code, as `notices.rs:124-136` already does.

**Paths and isolation.** A path is shown inside an entry with bidi isolation marks, applied in the seam and not per call site. The notice seam already does this by hand (`text/notice.rs:1-33, 104-138`), and the other path values are not isolated today (LR-19). The proposal is that every path-valued placeable goes through one helper in `pg-client`, so the rule is in one place. The isolation default of Fluent stays off (`words.rs:36`) for the first release, because it would wrap every value (LR-18), and the helper is the place where it is switched on per argument for a right-to-left locale later.

### 5.4 Live switch, and the thread-local bundle

**Today.** The bundle is `thread_local!` (`words.rs:18-21`), built lazily per thread from the three English files, and the pseudo flag is a process-wide atomic (`words.rs:23-28`). The QML bindings are evaluated once (QQ-11), and Rust strings are stored once (the gallery's selection text at `crates/desktop/src/gallery/model.rs:305-313`, the toast's words set at `crates/desktop/src/notices.rs:297-300`). Threads that word lines are the Qt main thread, the desktop's main thread before Qt starts (`fatal`), the panic hook on whatever thread panicked, and the CLI's main thread. The inbox's follower thread only queues work to the Qt thread (LR-13).

**Restart-only design (superseded 2026-11-14 by the live switch below; kept for the costs it avoids).** The locale is chosen once in `run()` before any line is worded (3.5, 5.1). Each thread builds its own bundle from the chosen tag's sources, which are static strings. The chosen tag is the one piece of shared state: it is set once, in a process-wide cell that the thread-local initializer reads, before any line is worded. A thread that words a line before the set keeps the English bundle it built, so the set must precede the first `shown` call on every thread. Nothing enforces that yet: a line worded earlier pins English for that thread, and a second set is refused. Phase 2 detects a call before the set (a debug assertion and a test). The live switch replaces that rule with the generation counter below. A test should check that a line worded after the set is in the chosen locale on each thread. The bundle is built lazily, as now. The cost of parsing three files per thread is not measured (SF-24), and it is paid only by threads that word lines. The settings control writes `gallery.json` and applies the change at once under the live switch. Restart-only avoids the QML binding changes (QQ-11, items 1 and 2), the re-push of stored Rust strings (LR-14, item 3), and the Qt translator's `LanguageChange` handling. It does not avoid the stored technical text (5.5), which is not switched by any language, and the OS-language text (PE-06), which stays in the Windows display language.

**Live switch (decided 2026-11-14, built in phase 4).** The work the investigators list is these steps, and none exists today. (1) A generation counter in `words.rs` that `shown` checks, so each thread rebuilds its bundle when the generation changes (LR-14, the pseudo flag is the model to copy). (2) A `revision` property with `NOTIFY` on `Words`, read by every binding, so QML re-evaluates (the shell's `qproperty` pattern at `crates/desktop/src/shell_bridge.rs:20-36`, and the change pump in `crates/desktop/src/pump.rs`). (3) Re-push of the Rust strings that are cached: the gallery's selection text, the toast, and any inbox row text. (4) A `QTranslator` and `LanguageChange` handling for Qt's own strings, which needs a translator loaded from the deploy folder (5.7). (5) `QLocale::setDefault` on change, and `Qt.locale` bindings that depend on a locale property. The investigators did not estimate the cost in time. The acceptance test for it would be that a switched screenshot equals the restart screenshot for the same locale.

### 5.5 Stored and persisted text

The policy has five classes, and each one has a rule that a migration, a test or a review can check.

1. Identifiers and codes are never translated. These are notice kind codes (`notice.rs:784-842`, with the golden lines in `crates/model/src/notice/golden.jsonl`), refusal codes (`refusal.rs:58-84`), source codes, enum keys (strum snake_case; `detection.rs`, `format.rs`, `media.rs`, `query.rs`), facet and sort keys (`lifecycle.rs:406` writes `"key":"name"`), QML action codes (`keymap.rs:1-8`), picker purposes (`picker/state.rs:8-27`), log targets (the source code, `inbox.rs:970`), CLI flags, the CLI's CSV header and status values (`borders.rs:96-130`), Fluent ids, environment variable names, and file extensions (PE-14, RS-15).
2. Notices are worded when they are read (PE-03, SF-20). A stored notice is re-worded in the active language, so a translation needs no migration of the notices table. A notice posted in one language and shown in another is correct by this rule.
3. Stored technical detail is kept as recorded. These are the `error: String` fields, `CatalogRebuilt.why`, `Carried::Nothing.reason`, `RoundPanicked.message`, `FileFailure.error`, the ledger tables, `CacheStartedOver.detail` (`notice.rs:444-448`) and `CacheDisabled.error` (`notice.rs:450-452`, from `app.rs:74`), which carry `pg_dbfile`'s `Damage` display (`judge.rs:46-53`), and the OS-supplied `file_system` and `Unreadable.error` values in `refusal.rs:14, 28, 38`. Damage is ours, so it is typed (phase 5). The frame is translated and the detail is labelled as detail, for example `{ $frame } (detail: { $error })`. The CLI prints `CacheStartedOver.detail` on its stderr (`crates/cli/src/report.rs:36-41`), and the user runs the CLI, so that stderr is a user surface (decided 2026-11-14). The doc comment at `crates/model/src/notice.rs:443-447` says the detail is "for the log" and is corrected in phase 5. Where the value is ours, it is typed instead of stored as English: the Yandex `Unexpected` details (RS-08), `CatalogRebuilt.why` becomes a code (RS-10, PE-01), and the scanner's `Display` becomes a typed `ScanBusy { root, holder }` (RS-13). OS error text stays in the Windows display language. The app can offer words for the common `io::ErrorKind` values, with the OS text kept as labelled detail (decided 2026-11-14: words for the common `io::ErrorKind` values in phase 5, with the OS text kept as labelled detail; PE-06).
4. Ledger rows keep the text they were recorded with (PE-02). Re-wording the frame does not change them, and the text is not re-read from the source.
5. User data is never translated and is shown isolated where it is a path (PE-12). This covers folder paths, file names, saved view names and their query JSON (which holds the user's file-name search text), and crop output names (`crates/crop/src/lib.rs:98-105`). The app's fixed names are identifiers: the crop's temp name `<out>.pg-crop` (`crop/src/lib.rs:212`), the writeback's temp names (`writeback/src/file.rs:40-46`) and the Yandex tokens (`yandex.rs:309, 319`). The Yandex tokens stay fixed (decided 2026-11-14).

Migration. None is needed for notices or prefs, because the language is a new optional key and the notice data is language-neutral (LR-03, PE-03). A new notice kind needs its `notice-<code>-title` and `-body` entries and a `source-<code>` entry in every locale, as `NOTIFICATIONS.md` already says ("Adding a kind", steps 1 to 4, SF-20).

The two docs that say nothing stored is English (`b5797ccf^:docs/temp/NOTIFICATIONS.md:12-13`, `crates/model/src/notice.rs:3-4`, `refusal.rs:1-3`) need a correction: codes and paths are language-neutral, and technical detail is stored verbatim (PE-04).

### 5.6 Logs, diagnostics and external tool messages

**Logs and diagnostics.** The log is an English diagnostic class. Its records are for maintainers, so a log message is not translated (decided 2026-11-14). The rule that makes this safe is the one in 5.2: anything a user should read is an entry, and the log is never the user's channel. The one exception the investigators found is `controller.rs:42-46`, which logs a refusal the user can cause (`--apply-view=NAME`) and which should become a refusal entry. The crash box's middle line is the English panic text (`panic_log.rs:23-32`, `text.rs:443-449`); it is a developer diagnostic inside a translated frame and stays English, which is the same boundary as the log (PE-11).

**ExifTool.** The app never changes ExifTool's language (no `-lang`, and no environment variable for the child, PE-08). Its stdout is parsed for `updated`, `unchanged` and `created`, and that parse contract is kept as it is. Its stderr is shown as technical detail inside the translated frame (5.5, class 3). The app's own bail messages (`exiftool/lib.rs:83-85, 153, 170, 181, 236, 249`) are English and move into typed errors, so the frame is words and the detail is stderr.

**FFmpeg.** `av_strerror` text is libavutil's string, loaded at run time, and stays as technical detail. The app's own literals (`no decoder for {codec}`, `ffi.rs:326`; `out of memory`, `ffi.rs:123`; `no picture size`, `video/src/lib.rs:122`) become typed decoder errors with entries, because they reach the inbox as failure text (PE-09).

**Yandex.** No request sends a language (the only header is User-Agent, `yandex/src/client.rs:50, 94`, `fetch.rs:36`), and no Yandex prose is shown. The live probe that the open question asked for is closed: no visible string would change, so it is out of scope (closed 2026-11-14). The `ureq` text (`yandex/src/http.rs:65, 69`) stays as detail, and the raw io error in `YandexNotStarted` (`crates/desktop/src/yandex.rs:371`) is classed the same way. The `YandexError::Unexpected` literals become typed variants (RS-08 proposes this), so the frame and each detail are words, and the English file gets one entry per variant.

**OS errors.** `io::Error` text in the Windows display language stays as detail (PE-06). The app's own words for the common `ErrorKind` values are added in phase 5 (decided 2026-11-14).

### 5.7 Qt's own strings, dialogs, fonts, mirroring and right-to-left

**Qt's strings.** The only Qt-owned text is the Save and Cancel buttons of `SaveViewDialog.qml:38`. Two routes exist. The first is a `QTranslator` that loads `qtbase_<tag>.qm` from the deploy folder, which needs windeployqt's translation step (the deploy passes `--no-translations`, `Justfile:57`), and the kit has the catalogues for 33 locales (QQ-07). The second is decided (2026-11-14): replace the two buttons with Words entries. The app has no other Qt dialog, so the route adds one entry per button and avoids a translator, a `LanguageChange` path and a deploy change. The licence and size of Qt's catalogues were not checked.

**Dialogs.** The Windows folder picker is the system's `IFileOpenDialog` (`picker.rs:132, 177-183`), and its text follows the Windows display language, not the app's. That is accepted and documented. The non-Windows `FolderPickerDialog.qml` uses Fluent labels and is covered.

**Fonts.** No font is shipped, and no family is set except `monospace` for log times. Fallback for Arabic, Hebrew, Indic and CJK scripts is Qt's font-family fallback over the installed Windows families (`qfontdatabase.cpp`, `qfontengine.cpp`). The Windows per-character order was not traced, and coverage for these scripts was not verified. The plan is to check each candidate locale with a screenshot, and to bundle a font only if a check fails. For English nothing is needed. A second locale gets the per-locale screenshot in its onboarding (5.9), and a font only if a glyph check fails (see the second-locale onboarding in 5.9, which covers shaping for Arabic, Devanagari and Thai). A bundled font needs a licence entry in the docs, because `cargo-deny` does not see font files, and `deny.toml`'s allow list has no OFL entry (WT-09).

**Mirroring.** A right-to-left locale needs `LayoutMirroring` set on the root with `childrenInherit`, anchors that follow it, and the hard-coded x positions (`GalleryGrid.qml:136`, `FolderTree.qml:43, 47`) made relative. The arrow keys' meaning is a separate decision: `Panel::Step` and the grid's left and right keys mean back and forward, and Qt does not mirror key semantics (QQ-09). Right-to-left is not part of the first release (decided 2026-11-14).

**Sizes.** The fixed containers in 3.7 are the test targets for longer text. The pseudo-locale pads each line by a third (5.10). The minimum window width is measured in phase 1 (3.7), with the owner's sign-off (QQ-20), and no scenario tests a narrow window until then.

### 5.8 The web client and the shared .ftl files

The browser design says nothing about text (SF-02, `WEB_CLIENT.md:528` is the only mention of the words bridge). The web verdict rests on a spike that exists only in two scratchpads outside the repo. Decided: its source is committed under `eval/web-spike/` at a recorded commit, which `WEB_CLIENT.md` cites. The HTTPS phone run stays the phase 8 gate. The frontend is the shared QML app (`WEB_CLIENT.md:44-62`), so the words facade must work in the browser. The recommendation (SF-03) is to run the same Fluent engine in the browser, by compiling `pg-client` to WASM, as the web design already assumes it runs (`WEB_CLIENT.md:347-348`). The same `.ftl` files then serve both clients, and the Rust-side behaviours (isolation off, `NUMBER`, plural rules, the pseudo-locale, the parity tests) have one implementation. A JavaScript engine (`@fluent/bundle`) would need a twin for each of those, and it is the fallback only if the Fluent part of the WASM proves too large. Its size is measured in phase 8, because the WASM bundle grows by the Fluent part and each worker parses the files (SF-24, `WEB_CLIENT.md:474`). The spike's `.wasm` is 27.7 MB (`WEB_CLIENT.md:474`), a Qt build of the grid spike, so it says nothing about the Fluent part.

Two web-specific points follow. The browser supplies the language preference through `navigator.languages`, which takes the place of the OS language in the chain (5.1), and that is a proposal to check against the browser design. The threaded WASM build (`WEB_CLIENT.md:452-457`) builds a bundle in each worker that words a line, so the first-use parse cost (SF-24) is paid once per worker. The saved choice is per device, following the preference-scope row at `WEB_CLIENT.md:558` (decided 2026-11-14). The default is `navigator.languages`, and a user's override is kept in `localStorage`, wrapped in try and catch, because it is a per-viewer convenience and not a library setting.

The shared `.ftl` files need no packaging step on the desktop, because they are compiled into the executable (`include_str!`). The browser client gets them the same way, through the WASM build.

The Fluent decision's reason about a JavaScript client (3.9) is conditional. If the browser client is the shared QML app, that reason disappears, and the decision rests on the seam's own needs.

### 5.9 Translator workflow

**File layout.** One folder per locale, with the same three files as the English one: `crates/client/locales/<tag>/text.ftl`, `ui.ftl` and `cli.ftl`, where `<tag>` is a BCP 47 tag that `unic-langid` parses. The English folder is the source. The `LOCALES` table in `words.rs` (5.1) registers each locale. Adding a locale is one table entry and three files.

**The hosted tool.** The investigators checked three hosted tools and a fourth by community report, from search snippets and not from fetched pages, so the claims are unverified. [Pontoon](https://mozilla-pontoon.readthedocs.io) lists `.ftl` among its native formats, has a Fluent editor that falls back to the source editor for nested selectors, and is designed around Fluent. [Weblate](https://docs.weblate.org/en/latest/formats/fluent.html) has a monolingual Fluent format since 4.8 with a file mask, lists no plural support, and warns that its Fluent support is under development. [Crowdin](https://store.crowdin.com/ftl) lists Fluent as built in, but marks pluralisation and source editing as "No". Transifex has a community thread that says it does not support `.ftl` (date unknown, possibly outdated, [thread](https://community.transifex.com/t/project-fluent-support-ftl-files/3512)).

The decision, confirmed by the owner on 2026-11-14, is to start without a hosted tool. Translators edit the `.ftl` files through pull requests, and the checks of 5.9 run in `just lint` and `just test` on every change. A hosted tool cannot be relied on to check variables and selects for this project, because the weakest parts of the Fluent support in the tools above are exactly plurals and source editing, and the variable and select checks are what the project needs most (WT-04, WT-05). Pontoon is the tool to revisit if the project wants a translation community, because it is the one designed around Fluent. This is decided and confirmed by the owner.

**Checks in `just lint` and tests.** Three English parse tests already exist (`message.rs:308`, `cli.rs:450`, `words.rs:107`, each `assert!(try_new(..).is_ok())`), and the English id tests cover part of check 2. The checks below extend these to every locale and add the rest (WT-02).

1. Every file in every locale parses. A file with a syntax error is an error, not a silent drop (today's `words.rs:40` drops it).
2. The ids of a locale are compared with the English ids. An id that the locale lacks is reported as untranslated and falls back to English. An id that the locale has and English lacks is an error, because it is unused.
3. Variables: every `$name` in a translated entry must be a field the Rust `Message` sets (`message.rs:85-93`), and every field the English entry uses must appear in the translation. Today nothing checks either direction (WT-04, LR-23). The source sets are fixed by the callers: `ui.ftl` entries may use only `$count`, `$text` and `$other`, which `words::ui` passes (`words.rs:51`), and `ui.ftl` uses exactly those three today (4, 24 and 10 uses); `text.ftl` entries use the `Message::args` names; a notice entry uses that notice's fields.
4. Selects: a translated select without a default is already a parse error (`fluent-syntax-0.12.0/src/parser/core.rs:285`, so check 1 reports it), and this check covers the selector values the Rust side sends (for example the refused-reason codes at `text.ftl:93-112`, and the notice variants) are covered by the translation's variants (WT-05). Plural coverage is checked by sampling (decided 2026-11-14): for the locale's tag, `intl_pluralrules` is run on the integers 0 to 1000, and the categories it returns are collected. Every select in the translation must name each of them explicitly, because a missing category falls to `*[other]` without any message, so the check must fail on it.
5. Every entry formats with sample values without resolver error, using the same samples as `every_message_is_worded_by_its_entry` and `Notice::samples()` (LR-23).
6. Glossary terms are checked by a reviewer, not by a tool (below).

Where the checks run matters. The registry in 5.1 embeds every locale with `include_str!`, so a cargo test in `pg-client` can iterate the table with no file reads, which `clippy.toml` forbids in that crate (LR-16). That makes the checks a cargo test, run by `just test`, and `just lint` can run the same test through `cargo test` if it is needed there. A Python checker in `tools/` is the alternative, and `tools/lint.py:20-33` is where a step would go, but a second parser would then need a dependency that the investigation did not check.

A deliberately broken fixture locale, given as a test-only string, proves that the checks fail (this is the proof step for phase 3).

**Compile time and tests (decided 2026-11-14).** The compiler enforces the variant-to-id match (the exhaustive match in the `messages!` macro) and the Rust field types of each argument. The tests enforce the Fluent variable names, the select variants, the QML id literals (`words.rs`) and the notice samples. Checks 1 to 5 above are tests, and none of them is a compile-time check.

**The glossary.** The repo has no glossary. The proposal is a short `crates/client/locales/GLOSSARY.md` that lists the product's words and the words that must not be translated: "Photo Gallery", "catalog", "notice", "inbox", "library", "folder", "view", "rating", "crop", "borders", "Yandex", "pseudo", the names of the key glyphs, and the environment variables. It is Markdown and the existing markdownlint applies to it. Each locale has one named reviewer, who approves its pull requests and its glossary entries (decided 2026-11-14). The owner names that person. For English, the source, the owner is the reviewer. For pt-BR, the owner is also the reviewer (decided 2026-11-14).

**Onboarding a locale.** The investigators counted nine steps today (WT-07); the list below has eight, so the count needs rechecking. In order: create the three files with the English ids; add one `LOCALES` entry (5.1); make the chosen locale come from the selection chain rather than a literal `"en"` (`words.rs:33`); decide the fallback (5.1 says per message; the code today has none); accept the tag in the command line (`command_line.rs:271-273`); extend the tests, which read only the English files through `test_support.rs` and the `ENGLISH*` constants; add a screenshot scenario and record its reference with `--record` (`tools/compare_shots.py`); and confirm that the tag is a valid `unic-langid` tag with plural rules in `intl_pluralrules`. Then screenshot the locale, check shaping for Arabic, Devanagari and Thai, and bundle a font only if a glyph check fails (5.7). The guide for translators does not exist, and it is a proposal (WT-13).

### 5.10 Testing: the pseudo-locale, text expansion, per-locale screenshots and the multi-locale test set

**The pseudo-locale.** The pseudo-locale accents ASCII letters, pads each line by a third plus one, and brackets it (`words.rs:70-89`). It is applied to the whole line after formatting, so user text is accented too. It does not test right-to-left direction or isolation, plural forms, number or date formats, font coverage, the per-entry fallback, or the syntax of a translation (LR-21). It is not applied to CLI lines, because only the desktop calls `set_pseudo` (`lib.rs:130`). It is not applied to the Qt numbers (QQ-15). The key hints are entries in the working tree (5.2), so the pseudo-locale reaches them; applying `set_pseudo` to the CLI closes the second; the `Numbers` formatter (5.3) takes the pseudo-locale into its output.

**Text expansion.** The pseudo-locale is the only text-stress test, and the screenshot matrix runs it without comparing it (`compare_shots.py:131-136`). The rule (decided 2026-11-14) is that every fixed-width text label sets `elide`, so clipping cannot happen by construction. The existing `qml_text.rs` guard (line 91) is extended to require it. The two pseudo scenarios are recorded and compared, not left uncompared: the pseudo output is deterministic (fixed accents and padding), so the comparison is valid and catches a change that clips.

**Per-locale screenshots.** The matrix has 25 scenarios compared against a recorded reference, rendered offscreen at 1600 by 1000 with device pixel ratio 1 (`compare_shots.py:104-129`, `Main.qml:17-18`). Each real locale needs its own recorded reference, which `compare_shots.py` cannot hold today. Phase 4 must add per-tag references and per-locale scenarios (keyed by tag, not commit). The English reference stays the same. The matrix does not cover right-to-left (no scenario), narrow windows (no scenario), DPI scaling (no scenario), the Yandex results panel, bordered and animated fixtures (S-14.1's "not covered" list), or the native folder dialogs (QQ-16).

**The multi-locale test set.** Three locales are enough to test the design: English (the reference), pseudo (the stress test), and pt-BR, added in phase 4 (English is the first locale). A fourth, the deliberately broken fixture of 5.9, tests the checks. The English value tests (`text.rs:496-801`, `cli.rs:462-482`, `keys.rs:317-354`, `desktop/lib.rs:249-260`, `command_line.rs:646-700`) keep their English pins by running under a `with_locale("en", ...)` helper. The `--locale=fr` test (`command_line.rs:646-700`) changes, because `fr` becomes a valid tag once it is in the table. The thread-local bundle makes the helper a per-thread override, which must be reset between tests (a proposal to check when it is written).
