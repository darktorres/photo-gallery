# Adaptive read tuning, and replacing the CLI with a headless `Session` driver

## Context

Two linked problems.

**1. The pipeline's reader count and memory budget are constants** (`READERS = 8`, `(readers + workers) × 12 MiB`, `crates/jobs/src/pipeline.rs`), chosen on one machine. Measurements this session show the right value depends on the drive and on cache state:
- Raw whole-file reads, cache bypassed (24 MB files, MB/s at 1/2/4/8 readers): Exos 178/102/131/115, Toshiba 48/50/46/33, WDC 101/76/69/51. One reader was best on all three HDDs; file latency grew 6–17× from 1 to 8 readers.
- Raw random 1 MB reads, Exos: 94/132/148/156 MB/s at 1/2/4/8; p99 latency 31 → 293 ms.
- Real pipeline with the real thumbnail maker, warm cache (64 GB RAM, 12 CPUs): about 40–45 files/s on all three HDDs at every count. Decode is the limit there.
- `docs/reference/IO.md` (earlier, cold real files) measured the opposite: 8 reads in flight ~235 MB/s against 64 MB/s at depth 1. The controller therefore measures instead of trusting either.
- Not yet measured: SSDs, and cold-cache runs with decode included.

**2. The command line is a second implementation of the pass layer.** The pass crates hold the work once, but `crates/cli` re-implements which passes run, in what order, with what options, over which volumes, and what is done with each pass's stats. Reading both sides found 21 differences (CLI at `Normal` priority against the app's `BelowNormal`; each CLI drive group making its own full memory budget while the app splits one governed budget; `hash` and `borders` over the whole library in the CLI but per lane in the app; scan failures that end the CLI command but become notices in the app; no `checkpoint_passive` in the CLI; removal and discard logic written twice; and others). The user does not use the CLI. Its real uses are developer tooling: `tools/compare_shots.py:333` builds test catalogs with it, `tools/profiling/bench_data.py` and `scan_timing.py` run it, and IO.md, PROFILING.md, HEAP_PROFILE.md and START_PROFILE.md describe measurements taken with it.

Instruction throughout: churn is not a concern; the goal is the most proper design.

## Decisions (made by the user)

- **No back-compat.** There are no existing users: removed flags, settings and fields are removed outright, with no aliases, deprecation or migration of old preference files or catalogs.
- **Remove the CLI (option 2)**, replacing its developer uses with a headless `Session` driver over the app's own service (Part A). Everything the CLI could do is added to the `Session`, with no second implementation of the passes.
- **No public tuning flags.** `--readers`, `--workers`, `--buffer-mb`, `--slots` go with the CLI. Counts and memory come from the governor and the controller. A developer pin for sweeps is an explicit typed setting, not a hidden input: `RunnerConfig.pin_readers` and `pin_workers` (both `Option<NonZeroUsize>`), set by `Session` and by `pg-dev run --pin-readers N --pin-workers N` (a developer binary, not a user flag); the library reads no environment variable for it. It is not a second mechanism: it only chooses which existing `Readers` variant `Inner::options` builds (`Fixed(n)` when pinned, `Auto` otherwise). A pinned run never writes a learned profile.
- **Priorities:** `Idle` is never used; `BelowNormal` is the one background class, for every pass.
- **`--serial` and the `serial_drives` setting are removed** on both platforms. The Linux gap it covered (an opaque device and the real disk under it get separate lanes) is accepted.
- **Storage support starts small:** on Windows, NTFS on plain physical disks only; VHD/VHDX, Storage Spaces, RAID, iSCSI and unknown buses are refused. Linux is unchanged.
- **Retry works for import failures in the app** (today only the CLI flag could retry them).
- Learned reader counts are **persisted** per physical disk in their own file.
- Cold-cache measurements use an elevated standby-cache purge, **asking the user before each purge** (it changes machine-wide memory state).
- Already decided elsewhere and kept: the memory budget is a **soft** target (a file larger than the budget is read alone; a value above physical memory only warns); each process keeps its own pool.

## Part A: the headless `Session` replaces the CLI

### Design

- **Naming:** `pg_app::Session` already exists (`crates/app/src/reader.rs:213`), so the driver's type is `pg_dev::Headless`; this plan writes "`Session`" for short where it means it.
- **`Session`** in a Qt-free crate of its own: `crates/dev`, a library (`pg_dev`, holding `Session`) plus the `pg-dev` binary, with its integration tests in `crates/dev/tests/` (not in `pg_app`: a driver used only by tools and tests does not belong in a product crate; the `gallery` test binary cannot link Qt, so it cannot live in `gallery` or `desktop` either). It starts `pg_app::LibraryService` on a catalog folder (`start`, `add_folder`, `remove_folder`, `discard_removal`, `rescan`, `set_features`, `set_thumb_height`, `status`), waits until idle with a timeout, and returns typed results: counts, rounds, per-lane times, the tuner's decisions, failures. It holds no pass logic: it starts, steers and reads the app's service (`pg_library::Runner`: `start`, `idle`, `rounds`, `progress`, `lane_progress`, `stop`).
- **What `pg_app` needs for it (checked):** `Library.runner` is private and `Library::start` is `pub(crate)` with positional arguments (`app/src/library.rs:104`); `App::open(Config)` is public and Qt-free (`app.rs:80`). Add a typed `LibraryConfig`/`RunnerConfig` (pins, pass mask, `writer`) carried by `Config`, and `LibraryService` pass-throughs (`quiescent`, `set_passes`, `run_until_quiescent`). **`Library::start` always starts the `Writer`** (`library.rs:112`), so a headless run on a real catalog would write queued ratings and turns into the user's photo files, which the CLI never did outside `gallery write`: `RunnerConfig.writer` defaults to false for `pg-dev`, and only `pg-dev write` starts one.
- **`RunnerConfig`** (new; today `Runner::start` takes six positional arguments, `runner.rs:43-56`): `pin_readers: Option<NonZeroUsize>`, `pin_workers: Option<NonZeroUsize>` (`HEAP_PROFILE.md:15,17` needs `--workers 1` for deterministic allocation counts, so the flag it replaces needs a home), `passes: PassMask`, `writer: bool`.
- **`Runner` pass filter** (one small library change; `lane.rs:107-115` is a fixed list of seven passes, `schedule::round` needs no change): the mask is a live cell on `Shared` beside `HeightCell` and `FeatureCell`, set at start and changed between runs; lanes read it at the start of each round. `--height` is one `HeightCell`, so several heights in one `pg-dev run` are sequential runs with an idle wait between. (Earlier text, kept:) the round takes a mask of passes (`schedule::round` over a filtered pass list in `lane.rs:107-115`), so `Session::run(&[Pass::Thumbs, Pass::Placeholders])` runs those passes in the real round and skips the rest. The `Session` never calls the pass functions directly. Tests use the filter too.
- **`pg-dev`**: a new non-shipped binary crate `crates/dev` over `Session` (added to `tools/crate-layers.txt`), for scripts and for Claude: `run --catalog-dir D [--add F...] [--height N]... [--passes ...] --until-idle --timeout S`, `status`, `remove [--discard-pending]`, `write`, `perf FILE`. **Not ported: the eval commands** (`borders` with paths, `--csv`, `--stdin`, `--import-review`, and `dups`). ## Part C: the adaptive controller

### The controller: `crates/jobs/src/tuner.rs` (new)

A pure, deterministic state machine. No threads, no clock trait (the repo has none; the convention is a `Duration`/`now` argument, as in `control.rs` `Running::mark` and `coordinator.rs` `Probe`).

```rust
pub struct Sample { elapsed: Duration, paused: Duration /* ctl.paused_total() diff */, reads: u64,
                    disk_ns: u64 /* around the read only: no pool wait */, bytes: u64, oldest_read_ns: u64,
                    work_wait_ns: u64, permit_wait_ns: u64, work_busy_ns: u64,
                    pool_order_wait_ns: u64, pool_capacity_wait_ns: u64, active_readers: f32, files: u64 }
pub struct Decision { target: NonZeroUsize, reason: Reason }
impl Tuner { pub fn new(cfg: TunerConfig, prior: Prior) -> Self; pub fn update(&mut self, s: &Sample) -> Decision }
```

Signals per window (about 3 s, at least 16 reads): throughput (bytes/s and files/s); mean disk latency per read; `starved = work_wait / (workers × elapsed)` (workers idle for reads: read-bound, may explore); `blocked = (pool_capacity_wait + permit_wait) / ((active_readers + workers) × elapsed)` (readers wait for a buffer or a slot because the workers are behind, or workers wait for a CPU permit because other lanes hold the cores: decode-bound, hold). **Corrected after review against the code:** the first design took `blocked` from `read_send` and said CPU contention shows up as `work_wait`; neither is true. `read_send` times `raw_tx.send` into a channel bounded by `pool.slots` (`pipeline.rs:267, 309-312`) while leases are also capped by `slots`, so it practically never blocks; a reader held back by slow workers waits inside `Pool::take`, which `timing.read` counts as read time (`:285-307`); and the worker's `ctl.cpu_permit()` wait (`:347`) falls between `work_wait` (the `recv`) and `work` (which starts after it), so it is counted nowhere. New meters, all lock-free `Clock`s: `pool_order_wait` (waiting for the item's turn in the in-order grants) and `pool_capacity_wait` (waiting for budget or slots) split inside `Pool::take` (`pipeline.rs` ~805-850), and `permit_wait` around `cpu_permit()`. `oldest_read_ns` (the age of the oldest read in flight, from a per-reader start timestamp) lets the latency guard see a stall before the read completes, because a `Clock` only adds after the fact and a 5 s stall would land wholly in one window. Windows are compared by median and discarded when `paused` is non-zero (the sampler diffs `ctl.paused_total()`, `control.rs:307`), so a pause is not read as a throughput collapse.

The algorithm below is a **candidate, chosen before the data**: a hill-climb with a latency guard is robust, but a model-based estimator (fit service time against reads in flight and pick the knee directly, using Little's law) may be better, and the two measurements disagree (IO.md against the raw probe). The Meters phase therefore comes first, and the algorithm is confirmed or replaced against the simulator and the measurements before it is wired in; only the interface (`Sample` in, `Decision` out) is fixed now. Candidate thresholds are named constants in `TunerConfig`, provisional:
1. Start at the stored profile value, else a prior by drive kind (rotational 2, solid 4, unknown 3); bounds 1..=16.
2. Initial climb doubles the count while the gain stays at least 12% (above the Exos ±10% run noise), then refines by ±1. Compare 3-window medians against a decayed table of throughput per count.
3. Latency guard: mean latency above 2× the low-count baseline for under 5% throughput gain: back off one step (the Exos signature).
4. Back off and hold down (30 s, doubling to 5 min) when throughput falls below 0.88× the best at the next lower count.
5. While stable, probe one step every ~20 windows (down when above the minimum, else up), judged by the same 12% rule over 3 windows, so it re-adapts when the cache cools or warms. Skip probes while noisy or decode-bound.
6. Noise: hold and report `Noisy` when the coefficient of variation over 5 windows exceeds 0.35. Discard windows that are short, have too few reads, or span a count change. Act only when 2 of 3 windows agree. At most one change per 2 windows.

### Pipeline: `crates/jobs/src/pipeline.rs`

- **A seam for the read, so the whole loop is testable without hardware.** The pipeline opens and reads files directly (`read_whole`, `read_gather`, `pipeline.rs:628-700`, `pg_platform::file::open_read`), so no test can give it a disk with a chosen service-time curve, and the closed loop (gate, sampler, tuner, pool) could be tested only in pieces. **It is not a one-line seam** (checked): `Read::Gather.gather` is `fn(&mut std::fs::File)` (`pipeline.rs:114`), and a simulated disk cannot hand out a real `File` that sleeps. So the seam must own the read: `Options.source: Arc<dyn FileSource>` with `read_whole(path, &mut Vec<u8>)` and `read_gather(path, hint, gather)`, and `gather` becomes `fn(&mut dyn ReadSeek)` (a `Read + Seek` trait object), which changes the signatures of `pg_container::jpeg_import_bytes` and `png_import_bytes` and the two `Read::Gather` call sites in `crates/import/src/lib.rs:146-149`. Default `OsFiles` does what the code does now (including `pg_platform::file::open_read` and the size query `sized(file)`); the added cost is one virtual call per file. Add a `SimDisk` in `pg_jobs_testkit` whose reads sleep for a service time that depends on how many reads are in flight (curves from the Exos and SSD measurements, with a mid-run "cache warm" step, in scaled-down time). End-to-end tests then assert convergence and re-adaptation through the real pipeline, deterministically within bounds. This is in addition to the pure-controller simulator.
- **Gate.** Spawn `min(max, items.len())` readers (a pass of three files does not start sixteen threads) and gate them with `ReaderGate { target: AtomicUsize, lock, cv, stopped }`. `gate.enter(id, stop)` goes **before** `next.fetch_add` (line 283): the pool grants strictly in item order, so a reader must never park after claiming an index. A reader with `id >= target` parks on the condvar with a 100 ms timeout so it re-checks `ctl` and `stop`.
- **Release conditions** (a hang blocks the scope join): the gate opens on `halt`/`StopOnDrop` (lines 706-719) and on `ctl.wake`; it also releases when the items run out (a parked reader checks `next >= items.len()` on each timeout, and a reader that finds `items.get(i) == None` at line 284 closes the gate). Each needs its own test.
- **Meters.** Make `Timing` shareable (`Arc<Meters>`); add `reads` and `disk_ns` (timed around the actual `read_to_end`, lines ~637/662/700, separate from the pool wait that `timing.read` includes today) and a time-weighted active-readers integral. `Clock` stays lock-free (`Relaxed`).
- **Sampler:** a dedicated thread inside the scope wakes every window, takes deltas, calls `tuner.update`, stores the target in the gate; stops on `halt`. It cannot run in the sink loop, which blocks in `results.recv()` (line 383).
- **`readers_busy_pct`** (line 179) divides by `opts.readers`; use the time-weighted active count.
- **`Options`:** `readers: Readers`, `enum Readers { Fixed(NonZeroUsize), Auto(Tuning) }`, `Tuning { max, prior, profile sink }`. `Options::new` stays `Fixed(READERS)`; `Fixed` remains for crop jobs (`coordinator.rs:652`), tests and the developer pin. Slots and `buffer_bytes` derive from `max`.
- `Pool` is otherwise unchanged except for the two new wait meters inside `take`; its in-order grants and `BUDGET_WAIT` loop stay.
- **Gate order and lifetime (from review):** the reader loop is gate, then `ctl.checkpoint_until`, then `fetch_add` (a gate after the checkpoint lets a reader released after a pause claim one more item). `halt` (`pipeline.rs:706`, which takes `stop`, `pool` and `ctl`) also notifies the gate. The sampler waits on a condvar that `halt` and `StopOnDrop` notify, not a plain 3 s sleep, so no `thread::scope` join is delayed. The active-readers count is an RAII guard (the loop has `break` paths at `:289, :293, :310` that would leak a manual decrement). Readers claimed an index never park, and leases drain through the workers, so the in-order grants cannot deadlock on a shrink.

### Wiring (one path only: the app's lanes)

- `Inner` gains its drive binding (`DriveKey`, `Kind`), set beside `set_label` (`coordinator.rs:430-434`; that runs on every tick under the registry lock, so the binding is compared before it is changed and the tuner is re-seeded only when it differs), because a kept lane's drive can change. **The tuner is owned by the lane, not by a pass**: a lane runs many short passes, and a tuner made at each pass start would repeat its warm-up, cooldown, hold-down and probe timers every time and never converge. `Inner` holds a `LaneTuner` (one `Tuner` per **pass kind**, each with its learned table) that survives across passes and is re-seeded when the drive binding changes. **The optimum depends on how the pass reads, so the learned count is kept per pass kind, not per lane.** The passes differ: import reads only a hinted prefix of JPEG and PNG files (`Read::Gather`, `crates/import/src/lib.rs:146-149`, small reads that are latency-bound), while thumbnails, hashes, borders, placeholders and crop read whole files (`Read::File`, megabytes, throughput-bound), and videos are read by the worker itself (`Read::Streamed`; no reader is involved, so such items do not feed the sampler). A single count shared by import and thumbnails would make each pass start from the other's optimum and re-learn it. **The key is the pass kind (Import, Thumbs, Placeholders, Hashes, Borders), set by the pass in `Tuning`, not a class derived from the items** (corrected after review: import mixes `Gather` for JPEG and PNG, `File` for other formats and `Streamed` for video item by item, `import/src/lib.rs:140-151`, so no per-pass or per-window read class exists, and a class derived per window would flip the tuner's state mid-pass). Two further rules from the review: a table is updated only from read-bound windows (a decode-bound pass such as thumbnails learns a flat throughput-per-count curve, and a probe-down on it would drag the count to the minimum for the next read-bound pass); and a pass too short to fill a window (16 reads or 3 s) only seeds and carries the count, it teaches nothing. The persisted profile is keyed by (disk key, pass kind); `Inner::options` (`inner.rs:63-66`) hands each pass a handle to it in `Readers::Auto`, the pass's sampler feeds it, and the profile is written when the lane goes idle or retires.
- A lane is a connected group of physical disks, so tuning per lane is tuning per disk. With the Windows storage rule every lane's disks are known; a spanned volume is tuned as one unit.
- `CpuGate` unchanged: decode contention shows up as `work_wait`, which yields a decode-bound hold.
- **Memory is governed with the readers, in this plan (closes TYPE_MISMATCH item 5), not deferred.** The reader count, the in-flight files and the buffer budget are one coupled quantity, so tuning only the first leaves memory wrong. (1) **No `max_lent` bound** (dropped after review: two mechanisms where one does). The reader gate already bounds the reads in flight, and the static budget already bounds the bytes held; a `max_lent = target + 2 × workers` would only trim the buffered files by `max − target` buffers (at most 15 × 12 MiB), and `Pool.slots` is also the capacity of the `raw` channel (`pipeline.rs:267`), which `max_lent` would have to stay under. If the measurements show waiting buffers matter, it is added then, with that constraint. (2) **The lane's budget stays static; only `max_lent` follows the tuner.** If the budget followed the target, the governor's per-lane share would change with every tuner decision, and the budget feeds pool admission, which shapes the `work_wait` and `read_send` signals the tuner reads: a feedback loop, and one lane's target would move the other lanes' samples. So the governor splits the run's total among lanes on the static maximum, as now (`Options::budget(READERS, cpus)` seeds it at `coordinator.rs:179`; recompute it for the new maximum), and a lower target lowers memory only through fewer reads in flight. (3) The run's soft cap comes from **available** memory, not only a fixed quarter of physical: `min(physical / MEMORY_SHARE, held + available − headroom)`, where `held` is what the lanes' pools hold now. **Corrected after review:** the first formula, `available − headroom`, subtracts memory the lanes already hold (`available` is net of their buffers), so the cap would fall as the lanes fill and recover as they shrink, a ratchet. The governor cannot hold a changing cap as built (`Governor.knee` and `cap` are plain fields set in `new`, `governor.rs:95-105`, and `rebalance()` is called only at `coordinator.rs:555`, at lane retirement and registration): `cap` becomes an atomic with `set_cap`, and the coordinator's lane loop calls `set_cap` and `rebalance` on a timer (every few seconds, with hysteresis so small changes do nothing). Available memory comes from `pg_platform::memory::available_bytes()` (Windows `GlobalMemoryStatusEx` `ullAvailPhys`, Linux `MemAvailable`, and the fallback arm for other systems returning `None`, as `physical_bytes` has at `memory.rs:10, 25, 41`) added beside `physical_bytes` (`memory.rs`; the coordinator reads only total physical today, `coordinator.rs:178`). It stays soft: a file larger than the budget is read alone. This restores the memory-pressure signal agreed in the brainstorm and left out of the first plan.
- Developer pin: `RunnerConfig.pin_readers` (see Decisions); a pinned lane runs `Readers::Fixed(n)` and writes no profile.

### Persistence: `drive-profiles.json` (sibling `JsonStore`, not a `Prefs` field)

`Prefs` is user-visible, flat, with a field-order golden test; this is machine-learned data that can be deleted at any time. Reuse `JsonStore` (atomic, quarantines a corrupt file, defaults apply). The file sits in the layout's home folder beside the preferences (`Layout::home`, `layout.rs:61`; it is machine-level, so it survives a catalog rebuild). `pg-dev` runs with an isolated home by default (`Layout::in_home` under its work folder, as the tests do), so a sweep or a test never writes the real profile; using the real one is an explicit choice.
- Entry per (disk, pass kind): kind, stable reader count and range tested, MB/s, sample count, timestamp, OS build. The map is a `BTreeMap` (no `HashMap` in the workspace) and the type has `Default` (`JsonStore<T>` needs it).
- **Layering (corrected after review):** `JsonStore` lives in `crates/app/src/store.rs`, and `library`, where `Inner` and the tuner live, cannot depend on `app` (`tools/crate-layers.txt`). The profile map and a `ProfileStore` trait (`load`, `save`) are defined in `pg_library` (the value type in `pg_model`); `pg_app` implements the trait over `JsonStore` and passes it in at `Runner::start`, as `Drives` is injected today. `Session` and `pg-dev` pass the app's implementation over their isolated home.
- **Key:** a fixed 64-bit FNV-1a hash of `vendor|product|serial` (`DefaultHasher` is not stable across Rust versions, and no hash crate is a dependency of `platform`). A lane over several disks (a spanned volume) keys on the hash of its sorted disk keys, so its entry is its own.
- **Stable disk key:** a new probe in `crates/platform/src/drive.rs` through the `disk_fact` seam: Windows `STORAGE_DEVICE_DESCRIPTOR` vendor, product and serial; Linux `/sys/block/<d>/device/{model,serial,wwid}`. Key = hash of those. (`DriveKey` today is disk numbers or `dev_t`, not stable across reboots.) A disk without a serial (some USB bridges) gets no profile, only the kind prior.
- **Invalidation:** distrust an entry when older than 30 days, the kind differs, samples are too few, or the first window's throughput is more than 30% below the stored value. A stored value only seeds the start; the controller still verifies it. **One write rule** (the first draft had two): a lane writes its learned entries when it goes idle or is retired, and only the pass kinds whose table has at least 60 s or 200 reads of read-bound windows and whose last decision was stable.

## Risks and unverified items

- IO.md (depth helps on cold HDDs) conflicts with the raw whole-file probe: the thresholds are locked only after the phase 5 measurements.
- Windows' disk counters are localized and busy-percent saturates, so the controller uses the pipeline's own timings only.
- Shrinking cannot cancel reads in flight, only later claims: the reaction is one file late.
- The controller may chase antivirus or search-indexer load; the noise hold and decayed tables limit it, and it responds to latency whatever the cause.
- Unverified: the RAID-bus refusal on RST machines; which tools in `tools/` beyond `compare_shots.py` and the profiling scripts run the CLI; the cost of the `FileSource` seam on the Windows open path, and the struct-literal `Options` sites it and the typed fields break (the seven test literals in `pipeline.rs:1035-1333`, `pipeline.rs:1496`, `inner.rs:65`); thumbnails' speed at `BelowNormal` against `Idle`; whether the Linux opaque gap matters in practice; an existing test that asserts Retry does nothing for imports; what `words.rs` still needs from `cli.ftl`.
