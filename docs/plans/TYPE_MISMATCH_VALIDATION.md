## 1. The saved last file is lost after a rating, and a catalog error reads as no file (`crates/desktop/src/shell.rs:95`)

**Status.** The row-id defect is fixed in code (`fab0512c`). `Prefs.last_file` is an `Option<FileStamp>` (`crates/model/src/ids.rs:55`), written as `null` or an object (`crates/app/src/prefs.rs:114-157`), and a number of either sign reads as none. The stamp is identity, size and mtime today; the change below replaces size and mtime. The save takes the shown file's stamp with `Catalog::stamp_of` (`crates/desktop/src/shell.rs:95-98`). The start resolves it with `Catalog::find_by_stamp` in `Core::new` (`crates/desktop/src/controller.rs:61-65`), with the catalog open. `start_state` (`controller.rs:102`) is a function of the prefs and leaves `last_file` to that caller. Tests: `crates/catalog/src/lookup.rs` (`stamp_tests`) and `crates/app/src/prefs.rs`. The desktop tests have not been run; they need the Qt build, and Qt is at `C:/Qt/6.12.0/msvc2022_64`. The Qt sentinel sweep is in `docs/plans/QT_SENTINEL_SWEEP.md`.

**Defects, in the code as committed.**
1. **The saved stamp goes stale after a rating.** The stamp is identity, size and mtime. The app's own write-back changes size and mtime: the catalog takes the new values after the copy (`crates/catalog/src/queue.rs:376`). A rating therefore changes the stamp the prefs hold, and the restore finds nothing. The identity and the creation time do not change, because the write copies in place and does not rename a temp file over the original (`crates/writeback/src/lib.rs:5-6`, `crates/writeback/src/inplace.rs:1-6`). Measured on a synthetic file: an in-place rewrite changed size and mtime, and kept the creation time and the NTFS file ID.
2. **A rating followed by a quit saves nothing, when the rated file stays the current item.** The last file is saved only in the `SaveSession` branch of `fire` (`crates/client/src/controller.rs:629-631`), which `flush` runs only when a `SaveSession` timer is armed (`controller.rs:606-620`). `Event::Rate` does not arm one (`controller.rs:387`). A grid rating leaves the current item unchanged: `set_current_item` returns early on an unchanged value (`crates/desktop/src/gallery/model.rs:251-253`), and `selection_after` keeps the same file (`model.rs:158`). A viewer rating moves to the next picture (`controller.rs:389-402`); whether that reaches the grid's current item was not traced, so it is not claimed here. The prefs keep the stamp from the last selection change, which predates the rating. Traced from the code; not run.
3. **A failed catalog lookup erases the stored file.** The save writes `stamp_of(…).ok().flatten()` (`crates/desktop/src/shell.rs:95-98`), so a lookup error writes `None` over the stored stamp. The start (`crates/desktop/src/controller.rs:61-65`) resolves a lookup error to `None`, and the next save then writes whatever is shown over the stored stamp, which is `None` if nothing is. Either way a transient catalog error loses the remembered file, and nothing tells the user.

*Related, not reconciled:* `docs/plans/BOUNDED_MEMORY_PLAN.md` step 7.9 (line 1508) names `save_last_file(Option)` and `loadedAnchor`, which overlap this item's proposed Rust-side ownership.

*History:* before `fab0512c`, the prefs held an `Option<FileId>`, stored on disk as `-1` for none. A row id names a file only in the catalog that assigned it. The rebuild keeps ids (`crates/catalog/src/rebuild.rs:188`, and the high-water mark carried over, `rebuild.rs:284-297`), but a catalog made anew hands ids out again from 1, so a saved id could name a different file. The stamp replaced the id for that reason.

**Impact.** A file that was rated while it stayed the current item is not selected again at the next start, because the quit does not save the stamp that would restore it. A failed catalog lookup at the save or the start loses the remembered file, and nothing says so. No rating is lost: the write-back and the catalog keep it. Only the restored selection is affected.

**Fix (planned).**
1. **The stamp is identity and creation time.** `FileStamp` (`crates/model/src/ids.rs:55`) drops size and mtime and keeps `identity` and `created`. The catalog sets `created` once and keeps it (`crates/catalog/src/writers.rs:181`, `coalesce(created, …)`). Identity can be reused after a delete, but a new file gets a new creation time, so the creation time refuses a reused identity. A file whose platform gives no creation time (`created` NULL, `crates/platform/src/dir/listing.rs:27`) is not remembered. There is no fallback to size and mtime, because that brings back defect 1. `find_by_stamp` (`crates/catalog/src/lookup.rs:122`) matches the identity and `created` on a row that is not `missing`, and `stamp_of` (`lookup.rs:103`) returns no stamp for a NULL `created`. The catalog already uses the same rule: it displaces a row whose identity matches but whose creation times differ (`crates/catalog/src/writers.rs:300-305`). A NULL `created` is backfilled by the next scan that reads the file (`writers.rs:306-307`), so such a file becomes rememberable then, not never.
   - *Known trade-off:* the stamp does not refuse a file that another program rewrote in place. Measured on a synthetic file: a copy over an existing file kept its identity and creation time. The catalog treats that file as the same one too, and the old size-and-mtime stamp refused it. The restore therefore keeps the selection on a file whose content changed under the same name.
2. **The save runs at flush whenever the session has started, and at most once.** `flush` (`crates/client/src/controller.rs:606`) pushes `Command::SaveLastFile` when the start is over, unless `fire` already pushed one because a `SaveSession` was armed. `fire` keeps its `is_started` guard (`controller.rs:629`), so a start's options are not saved. The stamp is read on the window thread before the window's writes stop (`crates/desktop/src/lib.rs:187`), so the catalog is still open.
3. **The start takes the resolved file.** `start_state` takes `last_file: Option<FileId>` as a parameter, and the caller resolves the stamp in `Core::new` (`crates/desktop/src/controller.rs:59-65`). The 11 test calls in `controller.rs` (lines 233 to 320) and the one in `crates/desktop/src/shell.rs:752` pass the argument.
4. **A catalog error is reported.** A new notice `LastFileNotKept { error }` (key `last-file-not-kept`, `Level::Error`, `Source::Catalog`) follows the steps for adding a kind in `crates/model/src/notice.rs:36-57`:
   - the variant and its `ids!` string (`notice.rs:800`, `:1168`), and the `level` (`:1285`), `source` (`:1313`) and `lifecycle` arms;
   - its sample in `Notice::samples()` (`:1617`), its line in `notice/golden.jsonl`, and its `ordinal` arm. The ordinal is 51: `ChangesUnseen` is 50 (`:1702`), so `KINDS` (`= 51`) becomes 52;
   - its row in `notice/resolver_table.golden`, its words in `crates/wording/locales/en/text.ftl` (`msg-notice-last-file-not-kept-title` and `-body`), and its `error` argument in `crates/wording/src/notice.rs` (the arm at `:95`, as `SessionNotRead` has). The `notice.rs` doc comment names `client/src/text/notice.rs` for the args; that file does not exist, and the doc is stale.
   - Its resolver is `Resolver::NextSuccess(Op::LastFile)`. `Op` (`notice.rs:931-952`) has no such variant, so one is added. A save reports success through `app::observe(Op::LastFile, …)` (`crates/desktop/src/app.rs:29`), which the prefs save does not do today. A successful save of no file clears the notice too.
   - The notice is posted where the outcome is, in the desktop save and start. A notice raised at the flush is not shown: the inbox closes in `App::shutdown` (`crates/app/src/app.rs:210-211`), after the flush. It is posted and, at most, logged. Whether it reaches the log file was not checked.
5. **A save whose lookup fails writes nothing.** `app::observe(Op::LastFile, catalog.stamp_of(file), …)` returns `None` on failure (`crates/desktop/src/app.rs:29`, failure arm at `:35-38`), and the save skips the `save_prefs` call on `None`. This is what stops defect 3 from erasing the stored stamp.
   - *Open decision:* a start whose lookup failed shows nothing, and a later successful save of nothing writes `None`, which erases the stored stamp. Keeping the old stamp until a file is shown would avoid that, but then a file the user really closed on would also be kept. Not decided here.

**Disk format.** `null` for none; an object with the stamp's fields for a file; a number of either sign reads as none. An object written before this change, with size and mtime and no `created`, fails to read as a stamp and so reads as none. The untagged read falls through to `Other`, so the last file is forgotten once and the prefs file still loads. A row id from an earlier catalog is never resolved, because it has no meaning here.

**Why not the alternatives.** Size and mtime change with the app's own writes (defect 1). A path breaks on a rename, which the restore should survive. A content hash changes with every write. The catalog itself would lose the value on a rebuild, and the prefs file is where it outlives one (`crates/app/src/prefs.rs:1-4`).

**Tests.** Written, against the current size-and-mtime stamp (they change with step 1): a reused identity with other size or mtime selects nothing (`a_reused_identity_is_a_different_file`); a renamed file keeps its stamp (`a_renamed_file_keeps_its_stamp`); a missing row selects nothing (`a_missing_file_is_not_selected`); a displaced row has no stamp (`a_displaced_row_has_no_stamp`) (all in `crates/catalog/src/lookup.rs`); `null` reads as none, and a number of either sign reads as none and is not resolved (`the_last_file_is_its_stamp_and_a_number_reads_as_none`, `crates/app/src/prefs.rs`).

**Planned, not written:**
- a rated file is still found after the app changes its size and mtime (`lookup.rs`);
- a file whose `created` is NULL has no stamp and is not remembered (`lookup.rs`);
- a stamp written and read back as one value (`prefs.rs`);
- an object saved with size and mtime reads as none, and the prefs file still loads (`prefs.rs`);
- a fresh catalog that holds the saved file under other row ids restores it, by identity and `created`; a fresh catalog that does not hold it selects nothing. The test `a_stamp_finds_its_file_by_identity_whatever_its_row_id` (`lookup.rs`) is named for the row id, but it changes `file_ref`, so it is renamed or replaced by these two cases. The first case is the design's intent: a rebuild of the same library keeps the selection;
- a file rewritten in place by another program keeps its stamp (the known trade-off above), so the test documents it rather than refuses it;
- a save whose lookup fails writes nothing and posts `LastFileNotKept` (desktop, needs a seam to inject the failure);
- a rating followed by a flush saves the last file (`crates/client/tests/controller_laws.rs`, beside `a_pending_session_save_is_made_at_the_close_with_the_last_file`);
- a failed start reports `LastFileNotKept`, and the notice's own checks pass: the sample, its golden line, the `ordinal`, the resolver table and the words (`crates/model/src/notice.rs`, `crates/wording`).

**Out of scope.** The Qt sentinel sweep (`docs/plans/QT_SENTINEL_SWEEP.md`); counts and positions (item 4); and the overlap with `docs/plans/BOUNDED_MEMORY_PLAN.md` step 7.9 (line 1508), which names a `save_last_file(Option)` that this item does not add.

**Not verified.** The rate-then-quit trace is from the code and was not run. The new stamp's NTFS behaviour is measured on synthetic files in the scratchpad, not on the library. Whether a viewer rating reaches the grid's current item was not traced. Whether a notice raised at the flush reaches the log file was not checked.

## 2. CLI accepts buffer size megabytes that saturate (`crates/cli/src/args.rs:58`)

*Changed at `9d167729`: the wrap is gone.* `buffer_mb` is now `Option<u64>` (`args.rs:45`), and the line is `opts.buffer_bytes = self.buffer_mb.map_or(budget, |mb| mb.max(1).saturating_mul(1 << 20))`. A value too large for a byte count no longer wraps to a small budget. It saturates to `u64::MAX`, which `Budget::new` (`crates/jobs/src/governor.rs:76`) keeps as an effectively unlimited budget. So the old claim that such a value serialises reads through `Pool::new` is no longer true. The value is still accepted silently, and the byte count is not checked.

**Impact:** an absurd argument is accepted and its limit is silently ignored. No data or hang impact.

**Fix (planned):** check the conversion in the clap `value_parser`, using `checked_mul(1 << 20)` and rejecting a value whose byte count does not fit. The parsed field holds bytes, so `options()` does no multiplication at all.

*Closed since the first list:* the thumbnail height entry is fixed. `ThumbHeight` (`crates/model/src/size.rs:82`) holds the 16 to 2048 range (`THUMB_HEIGHT`, `size.rs:12`), and the CLI parses it with a clap `value_parser` (`crates/cli/src/args.rs:131`, parser at `args.rs:190`). `pg_thumbs::run` and `ImageRequest::thumb` take it. The plan's `ThumbHeight::clamp(u32)` was not built. The UI clamp in `client/src/image.rs` is gone, and `ThumbHeight::for_row(RowHeight, Scale)` (`size.rs`) does that job instead.

## 3. XMP packets with a UTF-16 or UTF-32 encoding are decoded as UTF-8 (`crates/metadata/src/xmp.rs:62`)

`String::from_utf8_lossy(packet)` decodes the XMP packet from `crates/metadata/src/lib.rs:76` as lossy UTF-8. There is no BOM or UTF-16/32 detection anywhere in `crates/metadata/src`, as checked at `9d167729`.

**Impact:** for a JPEG whose XMP packet is UTF-16 or UTF-32, the rating and dates from XMP are dropped. The EXIF fallback still applies.

**Fix (planned):** detect the packet's encoding from its byte order mark, or, without one, from the null-byte pattern of its leading `<?xpacket` bytes. ExifTool and Exempi both do this. I could not confirm the normative wording in the XMP specification, so the rule follows those implementations. Decode it strictly into a UTF-8 `String` (`String::from_utf16` for UTF-16, `char::from_u32` per 4 bytes for UTF-32). A packet that does not decode is skipped, so its values are absent, not partly read. quick-xml then reads UTF-8 as it does now. `docs/plans/EXIFTOOL_PORT_PLAN.md:295` already plans the detection.

*Closed since the first list:* the version counter entry (old item 7) is gone. No version role, `cast_signed()` or `>= 0` version gate remains in the desktop, the QML or `client/src/grid.rs`. The last commit that touched `ROLE_VERSION` is `d28e2f72`.

## 4. Counts and positions are 32-bit at the Rust↔QML boundary (`crates/desktop/src/rows.rs:31`)

*Related, consistent:* `docs/plans/BOUNDED_MEMORY_PLAN.md` decision D29 (exact `f64` ranks and counts, decimal file ids, line 131) and step 7.9 (`qt_int` and `to_i32` deleted, line 1510) match this item's fix. The plan's windowed model also covers its window-slide and stale-reference concerns, which are not listed here.

`qt_int` (`crates/desktop/src/rows.rs:31`) clamps any count or row to `i32::MAX`. The copies the plan named are gone: `failed_files.rs` now calls the shared `qt_int`, and `notices.rs` has no copy of it. `facet_choices.rs:29` clamps an `i64` count. The bridge properties are `i32`: `gallery_bridge.rs:42` (`count`), `:56` (`current`), `:61` (`viewing`), `:63` (`anchor`), `filters_bridge.rs:37-38` (`total`, `matching`), and `shell.rs:127` (`list_shown(count: i32)`, declared at `bridges/shell_bridge.rs:61`). `gallery_bridge.rs:187, 192` already take and return file ids as `i64`. Qt's model API is `int` as well: `rowCount` returns `i32` (`facet_choices_bridge.rs:63`, `failed_files_bridge.rs:50`, `folders_bridge.rs:50`, `gallery_bridge.rs:131`). No windowed model exists yet at `9d167729`.

**Impact:** a catalog of 2^31 − 1 items or more (about 2.1 billion) shows a clamped count, silently, and items past that index cannot be addressed. A single flat Qt model cannot hold more than 2^31 − 1 rows.

**Fix (planned):**

- Counts and positions cross as `i64` in Rust and as `real` in QML. A JS number is exact to 2^53, about 9 × 10^15. The `int` declarations in the QML files become `real`. `qt_int`'s saturation is replaced by a checked conversion that fails loudly.
- The Qt model exposes a window of rows around the viewport, kept under 2^31. Rust keeps absolute positions as `i64`. A flat model cannot reach billions of items, so the gallery needs the window.
- The Qt sweep's selection (`docs/plans/QT_SENTINEL_SWEEP.md`) must address a window row with an absolute `i64` position, or the file's identity. Any Qt-side row handle inherits the 32-bit row limit. (The `QPersistentModelIndex` plan is withdrawn.)
- *Probe P5 (property level):* QML doubles round-trip exactly up to 2^53 for integers.
- *Probe P10 (rendered):* a marker inside a `Flickable`'s content item, moved by `-contentY` in the scene graph, lands on the wrong row from `contentY` 2^24 and collapses by 2^28, because of float32 spacing. A sibling marker whose y is computed in double is exact up to 2e11. So any `real` or `i64` position that reaches the scene graph must stay viewport-relative and sit outside the moving content item. The earlier P5 claim that a `Flickable` at 2e11 "positions its children correctly" was a property check, and is withdrawn.
- *Window size (probe `window`, and `real` on the user's aspects):* the window (viewport ±1500 px) holds at most 4,140 items at 3840×2160 and 11,462 at 7680×4320 on the user's aspects (the synthetic aspects reach 4,333 and 11,977). Qt's 2^31 row limit is far above these. The 32-bit problem is in the total count, not in the window.
