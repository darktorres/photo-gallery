# Notifications plan: persistent inbox, failure ledger, dev log view

Status (2026-11-10): S1 and S2 done (see "S1 as built" and "S2 as built" below); S3 to do. Re-checked against `d2cbc13`; delivered in
three stages (S1, S2, S3), each its own commit. The reference for the code as it is: [NOTIFICATIONS.md](NOTIFICATIONS.md).

## S1 as built

S1 is as the plan says, with these differences, each the more proper of the two:

- The desktop depends on `pg-log` directly (`desktop: app client log model platform render trace`), not through
  `pg_app::reexport`: `pg-log` is a layer below `app`, like `pg-model` and `pg-platform`, which the desktop already
  names, and `app` does not use it in S1. S2's `Inbox` adds `log` to `app:`.
- `RatingPopup` is not a modal kind: it is a popup the grid owns, closed by any other key, so a global key passes it
  by. The kinds are `Inbox`, `Log`, `Library`, `SaveViewDialog`, `ViewsMenu`, `FolderPicker`, `Yandex`, `YandexPreview`.
- Dev mode is saved by the controller's `Command::SaveDevMode`, which the shell carries out with `prefs().update`, not
  by a `Settings` property: the shortcut's rule (save on the key, not on the start seed) is the controller's, and it is
  tested there.
- `ModalOverlay.qml` is a `FocusScope`: opening it gives the keys to the child with `focus: true`, so the log view's list
  has them at once, without a deferred `forceActiveFocus`.
- The plain-text rule covers every `Label`, `Text` and `TextArea` whose text isn't fixed words (22 of them), not the three
  the plan named, and a test (`qml_text.rs`) keeps it so.
- `StartOverReason` (M-45), `ScanNote` and `Carried` moved to `pg_model::notice`, with their old enums gone, so the
  notice holds them without a copy and the client words them from one type.
- The log sites were 36, not 34 (two added since `d2cbc13`); the table is in `NOTIFICATIONS.md`.

## S2 as built

S2 is as the plan says, with these differences:

- The catalog owns the stored form: `pg_catalog::inbox` writes a `Notice` as JSON and reads it back typed (one of a kind
  this build doesn't know is `Notice::Unknown`), so `pg-catalog` depends on `serde_json`, not `pg-app`. It is one module
  of its own (`inbox.rs`, beside `pair` and `dups`), not `browse/read/notices.rs` and `browse/writes/notices.rs`: the
  inbox is not browsing.
- `notices.root` is a foreign key to `roots(id)` with `ON DELETE CASCADE`, not an `AFTER DELETE ON roots` trigger: the
  same effect, declared, and it holds for every delete of a root. A `part` column beside the key lets a producer clear
  every part of a kind and folder.
- A state posted again with the same data keeps its read and dismissed marks (a held problem is not news each time);
  one whose data changed is unread again. A complete scan of a library folder *replaces* its kept notices
  (`inbox::replace`: posts what it found, clears the rest) instead of clearing and posting again, which would bring back
  every note the user had read at every rescan.
- The writer publishes the whole listing with each change, so the window never reads the catalog for the inbox; the
  `Notices` model takes it as it comes. A dismissal and "mark all read" change the rows at once and are queued.
- A clear of a kind the inbox holds none of sends nothing (an in-memory set of the kinds it may hold), so the window
  clears a kind at every read that works without queueing a write.
- `NoticeSink` is a trait (`post`, `replace`, `clear`), not an `Arc<dyn Fn>`: the job needs the three.
- The cache's events become notices by `pg_thumbcache::Event::into_notice`, a rebuilt catalog by `Rebuilt::notice`
  (replacing `carried_note`): the app and the command line share them, and the command line prints the notices' words
  (`text::notice_line`) for its refused folders, its rebuilt catalog and the cache's events (M-26).
- `LibraryService::add_folder` returns the folder, and `pg_scan::RefusedMount` holds it, as a `RulePath`, so the notices
  keep the exact folder (not its display text).
- The toast is in the status bar, where the job's message line was, and the bell is an "Inbox (N)" button: the status
  bar keeps its layout. A populated inbox's screenshot waits for S3's failing fixture file.
- The progress bar's "N failed" split is S3's, with the ledger it links to.

## Context

The thumbnail pass shows "1 failed" in the progress bar, but the user cannot see which file or why. The detail exists
and is thrown away (`ThumbStats.failures` is dropped in the runner's thumbs pass; `ScanStats.failures` is never read;
import and borders keep only counts). More broadly the app has no place for notices:

- Only the library job's `Notice` reaches the UI, as ONE status line holding the newest notice ("... (and N more)");
  `take_messages` empties the buffer each time, so there is no history (`desktop/src/library.rs`, `show_notices`).
- `pg_app::Note` (prefs unreadable, catalog rebuilt, cache events) goes only to `gallery.log`, in hard-coded English
  (`desktop/src/app.rs`).
- `gallery.log` is plain text, unstructured, uncapped, with 34 `log::note` call sites.

Outcome: a persistent, dismissible INBOX (bell + unread badge); a per-file FAILURE LEDGER whose summary entries the
inbox shows; a dev-mode LOG view; and the progress bar's "N failed" opens the entry that lists the failing files, with
Reveal / Copy / Retry.

Standard set by the user: the MOST PROPER design; churn is not a concern. This plan has had eleven
adversarial reviews against the code (several executed the SQL in SQLite 3.49 or prototyped the Rust); this thirteenth
revision is re-grounded against `d2cbc13`, after the whole M-series (see Base).

## Decisions made with the user

- Inbox and persistence go together; the log is a separate consumer. Log = JSON lines, size-capped, rotated; legacy plain lines still display as info.
- Dev mode: `dev_mode` pref (also `--dev=1` / `PG_DEV=1`, session-only) + shortcut; off by default; when on, a Log button appears.
- Every user-visible warning and error is recorded in the inbox, including failures of actions the user just took (high-frequency sources coalesce). Internal diagnostics stay in the log (the per-site table records each site's level and reason; an audit at build time confirms none of the "log only" sites is user-visible).
- Toasts: info auto-clears (~6 s); warnings/errors stay until dismissed or replaced; a new inbox entry raises one toast that opens the inbox.
- Inbox in `catalog.sqlite` (migrations `TO_3`, `TO_4`); log in a new Qt-free crate `pg-log`.

## Design

### 1. Model (`crates/model/src/notice.rs`, new; `serde` + `strum` (+ the crate's existing `arrayvec`, optional `specta`), no `serde_json`, no `PathBuf`/`std::time`; wasm-safe)

- Layering (verified): `pg-jobs` -> `pg-platform` only; `pg-client` -> `pg-model` only; `pg-library` sees `pg-model` but neither client nor app; `pg-app` depends on `pg-library` (so nothing `pg-library` needs may live in `pg-app`); `desktop` reaches everything else through `pg_app::reexport`. So `Notice` lives in `pg-model`, `pg_client::text` words it directly, and the desktop mapping layers (`notice_text`, `note_text`) disappear. JSON encode/decode lives in `pg-app` (`serde_json`; model has it only as a dev-dependency).
- `Level {Info, Warning, Error}`; `Source` = the inbox category enum (Scan, Import, Borders, Thumbs, Crop, Writeback, Prefs, Catalog, Cache, Folders, Library, Edit, Update, App). Log records do not use it.
- `Notice` is a scalar-only enum merging the library `Notice` + app `Note` + desktop messages + new variants. Paths are `String`; the runner's `Err(Notice)` stays small (`result_large_err`).
  - Existing library variants (`pg_library::runner::Notice` at `d2cbc13`): `UnreadableFolders` (renamed `ScanUnreadable`), `ScanFailed`, `RootRefused`, `MountRefused{root, mount, reason}`, `ScanNote` (kinds include `volume-id`, `VolumeFallback`), `RoundFailed`, `RoundPanicked`, `CacheFull{height, made}`, `Cropped{folder, .., first_error: Option<FileError>, refused: Option<Box<pg_crop::CropError>>}`, `CropFailed`. `pg-model` sees neither `pg-jobs` nor `pg-crop`, so `Cropped`'s `FileError`/`CropError` and `folder: PathBuf` flatten to strings at the runner. Write-back failure, stopped and dropped are **not** runner variants: they come from the writer status the desktop reads (`refresh_writes` in `desktop/src/library.rs`) and are listed with the desktop messages.
  - App `Note`s: `Note` carries prefs events (`PrefStore`) and `Note::Thumbs(pg_thumbcache::Event)`. There is no separate `CacheStartedOver`: the cache `Event` (`thumbcache/src/types.rs`) has **five** variants — `TotalsFixed`, `TouchesNotWritten`, `NotStored`, `WalNotMerged`, `StartedOver{reason, path, detail}` — and **every** one maps to a `Notice` with its ftl. Also `CatalogRebuilt`, `PrefsUnreadable`, `PrefsNotSaved`. `App::open` synthesizes `NotStored{"cache disabled"}`. `App::shutdown` synthesizes `WalNotMerged` when the keeper close fails: that fires after the inbox has closed, so it is **log-only** (and gets its own wording, since it is not a cache event).
  - Desktop/edit messages (today worded by `text::*` in `desktop/src/library.rs` and the gallery/shell/picker modules): `WriteFailed`, `WriteStopped`, `WriteDropped`, `FolderNotAdded`, `FolderNotRemoved`, `FolderRefused`, `RescanFailed`, `LibraryUnavailable`, `FoldersUnreadable`, `PickerFailed`, `ListingFailed`, `RowReadFailed`, `ReloadFailed`, `FacetsFailed`, `TreeFailed`, `CropRefused`, `EditFailed`.
  - New: `ThumbsFailed`, `BordersFailed`, `ImportFailed` (virtual ledger entries), `UnreadableFiles{pass,count}`, `NoticesLost`, `FileNoLongerInLibrary` (reveal toast), reserved `UpdateAvailable`, and `Unknown`.
- **Every variant has a `Lifecycle`:**
  - `Event`: one-time, never keyed: `Cropped`, `CropFailed` (with `Detail`), `CatalogRebuilt`, cache `StartedOver`/`TotalsFixed`/`WalNotMerged`, `PrefsUnreadable`, `RoundPanicked`, the `ScanFailed` forget/temp-file errors, `FolderNotAdded/Removed/Refused`, `RescanFailed`, `LibraryUnavailable`, `FoldersUnreadable`, `PickerFailed`, `CropRefused`, `NoticesLost`.
  - `Transient` (toast + log only, never inbox): user-immediate info feedback (`folder_already_added`), `FileNoLongerInLibrary`, and `Unknown`. `UpdateAvailable` (reserved) is an `Event`.
  - `Ledger{pass}`: a **virtual** inbox entry built at read time from the failure ledger / the import join (2): `thumbs-failed`, `borders-failed`, `import-failed`. Never stored as a notice row.
  - `State{key, Resolution}`: keyed; replaced or cleared by a producer; coalescing count; throttled: `scan-unreadable:<root_id>`, `scan-note:<root_id>:<kind>`, `root-refused:<root_id>`, `mount-refused:<root_id>:<mount>` (posted per `refused_mount_list` in the runner's scan pass; replaced on a complete walk, cleared by the roots trigger), `cache-full`, `cache-touches`, `cache-not-stored`, `write-stopped`, `write-dropped`, `write-failed`, `round-failed`, `prefs-not-saved` (cleared by the next successful save), `unreadable:<pass>` (replaced each complete pass, cleared at 0 and by the pass's empty-items early return in `thumbs::run`), `edit-failed:<op>` (the sites it replaces — rating, rotate, mark-border in `gallery/edits.rs` — fire on every keypress; a read-only catalog would otherwise flood the inbox), and the high-frequency `listing-failed`, `rowread-failed`, `reload-failed`, `facets-failed`, `tree-failed`; each cleared by the next success of the same operation.
  - **Scan keys:** the scanned `RulePath` may lie under a root (see the runner's scan pass): `scope` is the **covering root's id**, resolved through the catalog's roots at post time (the post is `INSERT .. SELECT .. WHERE EXISTS (the root)` so a scan finishing after its root's removal posts nothing). A walk of the whole root *replaces* that root's keys; a walk of a sub-folder only adds/replaces its own failures and never clears. Removing a root clears its keys by an `AFTER DELETE ON roots` trigger (`DELETE FROM notices WHERE scope = old.id`), which also covers the CLI's `remove` command and `add_root`'s subsumed-root deletes (`Catalog::add_root`); `INSERT OR REPLACE INTO roots` would skip it (recursive triggers off), so `add_root` keeps its DELETE-then-INSERT (comment in `schema.rs`). `roots.id` is recycled (plain rowid), which is why the cleanup is a trigger, not an app step.
  - `ReplaceKey`/`ClearKey`: a complete scan that finds none clears its keys; a complete pass with `!cache_full` clears `cache-full`.
- `FileFailure {file_id: Option<FileId>, folder: Vec<u8> (exact merged bytes), path (display), error, retried}`; `Detail` only for event notices and scan failures (capped ~200 entries / ~64 KiB). Error texts are capped. **Text hygiene when built:** control characters and newlines replaced; caps cut on a char boundary (`char_indices`/`get(..n)`; `String::truncate` panics); names via `from_utf8_lossy` for display only.
- `kind` = `Notice::code()`. `Notice` is internally tagged `kind`, kebab-case; `code(&self)` is `(&self).into()` via `strum::IntoStaticStr` (prototype: matches the serde tag); a test pins both. `Unknown { code: String }` is `#[serde(skip)]`, built only by the `pg-app` decoder (`serde_json::Value` fallback) and never re-serialized; a known tag with a missing required field also lands there and is logged; later fields `#[serde(default)]`; codes kept forever; `Notice::samples()` is a real `pub fn` + golden JSON per variant (mirror the `Prefs` `GOLDEN` test in `app/src/prefs.rs`). Not `specta::Type`. `code()`, `title_id()`, `body_id()` come from ONE macro/variant table.
- `Action {ShowFailedFiles, Reveal, CopyDetails, Retry, OpenInbox}` from `Notice::actions()`. `ShowFailedFiles` only for Import (`Choice::Status(Status::Failed)`, `model/src/query.rs`). `Reveal` is per ledger row. `Retry` is for `thumbs-failed`. Extension path for a new notice kind ("updates, or whatever"): one `Notice` variant (code, level, source, lifecycle, actions), its `Message` title/body + ftl, the producer call; badge, toast, persistence and writer are generic. A new `Action` (e.g. `OpenUrl` for an update) needs `Action`, the `Notices` dispatcher and a shell handler; written up as a checklist in `docs/NOTIFICATIONS.md`.

### 2. Storage (`crates/catalog`, layered as M-7 leaves it: `core.rs`, `lifecycle.rs`, `writers.rs`, `types.rs`, `sql.rs`, `browse/`)

Layer rule (the module headers: `core.rs` "uses `lifecycle`, `writers`, `schema`, `types` and `error`"; `lifecycle.rs` "uses `types`, `schema` and `error`; its SQL macros are from `sql`"; `writers.rs` "uses `types` and `error`"; the modgraph cycle check catches a reverse edge, since browse/writes/dups/pair use core). So: **`set_thumbs_version` goes in `lifecycle.rs`** beside `set_import_version`/`set_borders_version` (called from `Catalog::prepare` in `core.rs`), and the ledger SQL it needs (`failures_retry`, `failures_*`) lives in a new low module **`ledger.rs`** (uses `types`, `error`, `sql`'s macros; declared in `lib.rs` after `mod sql;`, since the macros are textually scoped; `ledger` added to `lifecycle.rs`'s "Uses" header; its items `pub(crate)`). Notice reads/writes are browse-level: `browse/read/notices.rs` (`browse/read.rs` has an explicit `mod` list) and, since `browse/writes.rs` is one file, it becomes a parent with `mod notices; pub use notices::*;` (a child-module `pub use`, allowed). `crate::writes` (the file-writes queue) is a different module. Write functions are free functions taking `&Catalog`. `data_version` is an `impl Catalog` method in `core.rs` (`deny.toml` allows `rusqlite` only in catalog-family crates). `pending_borders` (`core.rs`) gets its skip-row SQL inline; the borders ledger clear runs after the `BordersWriter` transaction (`Catalog::tx()`) commits, outside it. Migrations `TO_3_NOTICES` and `TO_4_LEDGER` are consts beside `TO_2_CHANGE_STAMPS` in `schema.rs` (appended to `MIGRATIONS`). `next_seq!()/seq!()` are in `sql.rs`.

**TO_3 (S2):**

```sql
notices(id INTEGER PRIMARY KEY, key TEXT UNIQUE, scope TEXT, uid INTEGER NOT NULL DEFAULT 0,
        level INTEGER NOT NULL, source TEXT NOT NULL, kind TEXT NOT NULL, data TEXT NOT NULL, detail TEXT,
        count INTEGER NOT NULL DEFAULT 1, created INTEGER NOT NULL, updated INTEGER NOT NULL,
        read INTEGER, dismissed INTEGER)       -- times: Unix seconds, as `scans`
  + INDEX notices_live(dismissed, updated DESC)
AFTER DELETE ON roots: DELETE FROM notices WHERE scope = old.id
```

- `uid` is stamped from `meta.seq` at insert (`next_seq!()/seq!()`, monotonic, carried with `meta`): `id` is a reused rowid and `created` has one-second resolution, so UI mutations address a row as `(id, uid)`; a stale one is a no-op.
- `notice_post` upserts by `key` (`INSERT .. ON CONFLICT(key) DO UPDATE SET count = count + 1, updated = .., read = NULL, dismissed = NULL`; executed: NULL keys never conflict, so events always insert; dedup on the summary fields only, never `detail`'s text; `ReplaceKey`/`ClearKey`). Methods: `notice_post`, `notices(limit)`, `notice_mark_read`, `notice_dismiss`, `notice_clear` (plain rows: dismiss all), `notice_prune`, `notice_unread_count`.
- Retention (writer, after each batch and at start): ~1000 live rows (oldest read first), dismissed purged after 30 days.
- **Backup (irreversible-migration mitigation):** in `Catalog::prepare` (`core.rs`), under the exclusive hold and before the first migration step, `wal_checkpoint(TRUNCATE)` then copy `catalog.sqlite` to `catalog.sqlite.pre-v<N>.bak` for the version being left, unless that file exists. Older builds refuse a newer catalog (the "newer than this build" check in `prepare`); downgrading = restore the backup. The catalog holds ratings/edits, which is why.
- Migration tests: the `== BASELINE_VERSION + 1` asserts in `schema.rs` tests become `BASELINE_VERSION + MIGRATIONS.len()`; `carried_is_every_table_of_the_baseline` builds `BASELINE` only and compares with `CARRIED` (a superset after this change): rewrite as `carried_is_every_table_of_the_current_schema` against `expected(current_version())`; extend the v1-migration test in the `lifecycle.rs` tests (`a_catalog_at_version_one_is_migrated_forward_and_keeps_its_rows`) to v1 -> latest. `notices` is added to `CARRIED` (independent of `files`); `copy_tables` drops all triggers, copies by common column name with ids kept, recreates triggers from their text (verified; the prototype re-created 27 triggers identically). Locking (`prepare`): the new build migrates under the exclusive hold and fails with `in_use` while an older GUI/CLI has the catalog open. Compatible with BOUNDED_MEMORY_PLAN D1/2.3.

**TO_4 (S3), the failure ledger and its acknowledgements:**

```sql
file_failures(id INTEGER PRIMARY KEY,
              file_id INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
              pass TEXT NOT NULL,                    -- 'thumbs' | 'borders'
              mtime INTEGER NOT NULL, size INTEGER NOT NULL, rotation INTEGER NOT NULL,   -- the file state it describes
              error TEXT NOT NULL,
              retry INTEGER NOT NULL,                -- thumbs: 0 = a panic, 1 = a decode error; borders: 0 (panic / decode error)
              serial INTEGER NOT NULL DEFAULT 0,     -- stamped from meta.seq by the insert trigger
              first_seen INTEGER NOT NULL,           -- Unix seconds; "first failed" in the expanded row
              UNIQUE (file_id, pass)) + INDEX file_failures_serial(pass, serial)
ledger_ack(kind TEXT PRIMARY KEY,                    -- 'thumbs' | 'borders' | 'import'
           seen_to INTEGER, read INTEGER, dismissed INTEGER)   -- seen_to: a serial (thumbs/borders) or a files.seq (import)
```

`TO_4` itself seeds `INSERT INTO meta VALUES ('thumbs_version', 0)` (the `BASELINE` is frozen, "comment edits only"; `SEEDS` compares `meta` keys, and `copy_tables` copies only meta keys `main.meta` already has, which the migration guarantees); both tables join `CARRIED` after `files`.

- **Why a ledger.** A failure list inside a notice cannot work (the pass keeps only counts; a file made later on demand or by the CLI is never relisted so its failure would stay forever; 100k breaks any cap). The per-file fact is a table. It stays in `catalog.sqlite` (not `thumbs.sqlite`): FK cascade, survival across a rebuild, one home for thumbs+borders, atomic across processes.
- **Triggers (only these):** `AFTER INSERT ON file_failures` stamps `serial` (`next_seq!(); UPDATE file_failures SET serial = seq!() WHERE id = new.id`; prototype: one distinct monotonic stamp per row, no re-fire since recursive triggers are off); `AFTER UPDATE OF mtime, size, rotation, missing ON files` with the same `WHEN old.x IS NOT new.x` guards as `files_source_changed` deletes that file's ledger rows (a changed or missing file is a different state; this unblocks a `retry=0` row). The scan's unchanged path is `UPDATE files SET last_scan` (`writers.rs`: `seen`/`seen_identity`), which does not match `UPDATE OF`, so a quiet rescan pays nothing (measured: 0.30 s with and without at 200k files); a file delete cascades (tested: the cascade fires child triggers). No trigger writes `notices`.
- **Upsert, never `INSERT OR REPLACE`** (it would give a re-failing file a new serial): `INSERT .. SELECT .. FROM files WHERE id=? AND mtime=? AND size=? AND rotation=? ### 5. Log (`crates/log` = `pg-log`; deps pg-model (must be used, or `cargo machete` flags it), pg-platform, serde_json; `[lints] workspace = true`; a line in `tools/crate-layers.txt`)

- `Record {t_ms, level, target: String/Cow, message, detail, seq}`: `target` is free-form (the 34 sites span animation, video, providers, yandex, folders, views, session...); `detail` capped ~4 KiB; `seq` is a per-process sequence number. Items not used across crates are `pub(crate)`.
- JSONL encode/decode; legacy plain-line parser (`YYYY-MM-DD HH:MM:SS text` -> Info, kept as `legacy_time` wall-clock text and ordered by file order: `pg_platform::clock` has only `local_time()`; continuation lines of a legacy multi-line panic attach to the previous record's `detail`); a `session start` record per launch.
- **Writer:** keep the current **open-append-close per record** (`desktop/src/log.rs` `append`, `panic_log.rs`) with one `write_all` per record; **new:** the size checked by metadata and a `Mutex` serializing records (today neither exists). The path comes from `pg_app::Config.log_path` (= `pg_library::layout::Layout::log()`). `t_ms` comes from `SystemTime` in pg-log (`pg_platform::clock` has `local_time()` and `process_age_ms()`, no wall-clock millis). Rotation ~5 MiB x 3 (`gallery.log`, `.1`, `.2`) by rename; a held handle would follow a renamed file on Windows (std opens with `FILE_SHARE_DELETE`) and there is no single-instance guard, so no handle is kept open; a failed rename retries, then truncates the oversized file (never silently unbounded). Only the GUI writes `gallery.log` (the CLI uses `eprintln!`, verified). `pg-log`'s stderr fallback uses `#[expect(clippy::print_stderr, reason = ..)]` as `desktop/src/log.rs` does (`allow_attributes = "warn"` rejects `#[allow]`).
- **Ring:** in-memory, bounded by count (~5000) AND bytes (~4 MiB); fills regardless of dev mode (a runtime toggle must not lose history). Opening the Log subscribes to the live feed first, then loads the file tail off-thread, then merges by `seq` (no duplicates, no gap); fixed-height rows, detail in an expandable pane.
- **Dependency boundary:** `pg-app` depends on `pg-log` and re-exports it through `pg_app::reexport` only. `pg_log::warn/error/info(target, ..)` is for non-inbox diagnostics; inbox-worthy events go through `Inbox::post`, which logs them. All 34 sites migrate in S1 (their inbox half in S2); no wrapper kept; the desktop `log.rs` module is deleted. `panic_log.rs` keeps its write-result contract (`internal_error(..., log_error)`): it writes a record via `try_lock` (a poisoned lock is recovered) with a raw JSON-line fallback.

## Risks

- Inline SQLite writes can stall 5 s behind an import: all app-originated writes are on the writer thread, the UI is optimistic, the provider never queries the catalog on a cache hit.
- The migrations are irreversible: a pre-migration backup is made once per version; older builds refuse a newer catalog.
- The base may move again after `d2cbc13` (the M-series is done, but other work lands): cite symbols, re-read each file before editing it, and re-run the `log::note` count and the `Versions {` grep at the start of each stage.
- `THUMBS_VERSION` is bumped by hand (codec dependency upgrades are not detected): documented.
- Shutdown order (cache close -> forwarder join -> inbox close -> catalogs/pool -> keeper).
- Persisted rows are typed values worded at display time: editing ftl re-words old rows; `code()`s are permanent.
- Global shortcuts rely on Qt matching a `Shortcut` before `Keys` handlers: read in the Qt source, proven at build time by `tst_global_keys.qml` (fallback: guard the grid/viewer letters with `mods.ctrl` and use a root handler).
- A native decoder segfault still loops on every launch, as it does today (out of scope).
- If a stage shows many compile errors, fix in order model -> render/catalog -> thumbcache/thumbs -> app/library -> client -> desktop -> QML.
- Out of scope: an update checker (`Update` source + reserved variant only); system toasts while backgrounded; Retry for borders (rows clear on a version bump); Linux I/O priority; the scroll-hitch and thumbnail-starvation investigation (separate plan).
