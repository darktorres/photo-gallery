# Callgrind drill: the 11 benches at 1bb0390

Findings from a full drill of each profile in `1bb039084.tar.zst` (the bench run of commit `1bb0390`, archived by
`tools/profiling/wsl-bench.sh`). Read it with `docs/PROFILING.md`. Every profile was read with `tools/profiling/cgtab.py`
and, for the catalog benches, cross-checked against the bench catalog (`/root/pg-bench/v2-windows-rules/catalog.sqlite`,
read-only) and `EXPLAIN QUERY PLAN`.

Ir is instructions executed, not time. Each bench ran once, so there is no variance estimate. The numbers are
**measured** unless marked **inferred**. Items marked **unverified** are claims that were not checked against the source
or the profiled database.

**Revised.** Each candidate change and open question was then checked against the code and the profile (see "Validation"
at the end). Corrections are marked inline with **Corrected** or **Resolved**.

## Per bench

### `catalog::facets.all` (93,262,634 Ir, one call over 4,000 files)

- **Split:** libsqlite3 91.8%, libc 7.8% (malloc, mutexes, memmove), our code 0.3%.
- **Hot spots:** the borders statement is 41.4 M (44%), about 10 K Ir per file. The three count statements (matching,
  types, exts) are 51.3 M (55%). The total count is 0.6 M.
- **Cursors:** 16,052 `sqlite3BtreeCursor` calls, about 4 per file. These match the four `EXISTS (SELECT 1 FROM
  border_sides …)` subqueries in `border_class!`, one per class per row (**measured** count, the attribution is
  consistent with it).
- **Sorts:** `types` and `exts` use a TEMP B-tree for `GROUP BY`; `exts` adds `ORDER BY`. Text comparisons total 66 K
  calls, about 7% inclusive.
- **Fixture:** `ratings`, `file_writes`, `border_marks` and `border_sides` are empty. Every join misses. In addition,
  every `analysis.cut_*` is NULL, because the borders pass never ran on this layout (see Fixture). The join-hit and
  border-hit paths are never exercised.
- **Suggestion:** in `crates/query/src/lib.rs`, guard each `border_class!` EXISTS so it only runs when the bordered test
  holds, e.g. `CASE WHEN <bordered!()> THEN EXISTS(…) ELSE 0 END`.
  - **Checked: the rewrite keeps every sum.** NULL and 0 both add nothing to `sum()`, and both are false inside the
    `WHERE … OR` in `any()`. Nothing negates `border_class!`.
  - **Saving, measured in Ir:** with the guard applied in the WSL clone, `catalog::facets.all` went from 93,285,007 Ir
    to 75,040,488 (−18.2 M, −19.6%). The baseline was taken with the same probe build. The earlier wall-time estimate
    (about a quarter) was an overstatement.
  - **Equality is argued, not tested on data.** The bench catalog has no border rows (`border_sides` is empty), so
    every `EXISTS` is 0 before and after and the sums are trivially equal. The argument is by SQL semantics: NULL and 0
    both add nothing to `sum()`, and `coalesce` gives 0 for an all-NULL sum. A catalog with border rows would test it.
  - **Best case in the bench:** the fixture has every `cut_*` NULL, so `bordered` is NULL for every row, and the guard
    skips every EXISTS. Real libraries have `cut = 0` for most files, which also skips most rows. On a library with many
    bordered files the saving is smaller, and it is unmeasured.
- **Inferred, confirmed in outline:** SQLite evaluates both operands of `AND` in a value context, so the EXISTS runs
  even when the guard is NULL. The 16,052 cursors fit this.

### `catalog::list.all_name` (31,276,357 Ir, 4,000 rows)

- **Split:** libsqlite3 81.6%, bench-side Rust (`ir`, including rusqlite generics) 12.0%, pg_catalog 3.6%.
- **Path:** the query reads the `files_order` index. There is no SQLite sorter and no Rust sort, so the name order costs
  nothing extra. Measured by the absence of sorter symbols and by `EXPLAIN QUERY PLAN`.
- **Hot spots:** `entry_from_row` is 34.8% inclusive, about 2,700 Ir per row, with 15 column reads per row.
  `sqlite3_column_type` and `value_ref` account for most of that.
- **Count pass:** the `count(*)` that sizes the list is 0.6 M (1.9%).
- **Allocation:** negligible. About 5,500 SQLite mallocs and 8 Rust allocations.
- **Prepare calls (open):** 24 `sqlite3_prepare_v3` calls where about 4 are expected, and 4,022 `sqlite3_step` calls
  against about 4,004. Together about 1%. The 24 come from rusqlite's prepare path: 17 through `InnerConnection::prepare`
  and 7 through `execute_batch`. The call graph shows only two direct calls into each, so the callgrind call counts do not
  reconcile with it. The profile contains no setup functions (`open_catalog`, `Catalog::prepare`), so setup is not the
  source. The catalog's 45 schema objects do not match 24 either. See open question 1.

### `catalog::list.all_taken` (45,665,082 Ir, 4,000 rows)

- **Versus `all_name`:** +14.4 M (+46%).
  - `unixepochFunc` (the date fallback when `taken` is NULL): 10.0 M (21.9%), about 2,500 Ir per row.
  - The Rust-side sort (`sort_by`): 2.4 M (5.2%), about 600 Ir per element.
  - Key column read and extra VDBE self: about 1.8 M.
- **The fixture has no taken dates:** in a read-only copy of the bench catalog, all 4,000 `analysis.taken` values are
  NULL, so this bench only measures the mtime fallback. **Corrected:** the cause is a generator defect, not the library
  (see Fixture).
- **Timezone:** the WSL zone is America/Sao_Paulo. The `localtime_r` and `tzset` cost is environment-specific
  (**inferred**: the zone's transition table ends and the POSIX footer is re-parsed on each call). A Windows host may
  show different numbers.
- **Suggestion:** no code change. Fix the generator's EXIF date (see Recommendations) to measure the real path.

### `catalog::list.all_unrated` (31,501,895 Ir, 4,000 rows)

- **Versus `all_name`:** +225,538 Ir (+0.72%, about 56 Ir per file). 97% of the difference is extra VDBE self time, from
  one `NotNull` opcode per row (program 81 → 83 ops). The plan is unchanged.
- **The bench can't isolate the filter:** the ratings table is empty, so every file is unrated. The filter removes
  nothing, and the rating join runs in both cases. This number is the predicate's cost only. The generator writes no
  ratings, so the table stays empty by construction (see Fixture).
- **Suggestion:** no change for the rating filter.

### `catalog::list.folder_flat` (721,475 Ir, 50 rows, folder-00, non-recursive)

- **Split:** libsqlite3 82.9%, bench-side Rust 7.1%, libc 5.7%.
- **Prepare:** 266,856 Ir (37%). `list_grid` prepares two statements on each call: the count (via `query_row`, which
  prepares every time) and the grid SQL (via `prepare`). Code generation dominates (`sqlite3Select` 24%,
  `sqlite3WhereBegin` 12%).
- **Scaling:** the key range `[key, key+1)` returns exactly the 50 files, so rows scanned equal rows returned. All-in
  cost is 14,429 Ir per returned row here, against 7,819 for the whole catalog.
- **Fixed versus per-row (inferred from two runs):** about 335 K fixed plus about 7.7 K per row. About 46% of this call
  is fixed. The count pass is 28,309 Ir for 50 entries and 594,695 for 4,000, about 143 Ir per index entry.
- **Table seeks:** the profile's 7,400 per call do not fit the body's work (3,288 opcodes in total, and about 250 seeks
  predicted by the plan). See open question 6: an artifact of the profile's call counts, likely.
- **Suggestion (low value):** `prepare_cached` for the two statements. **Checked:** the SQL text is fixed per recursive
  flag and filter/sort, and the scope is bound parameters (`?`), so the cache keys are stable. The saving is about
  267 K Ir per call, which is small against the call's 721 K. The bench builds a new `Catalog` on every iteration, so it
  would show no gain unless the cache is warmed in setup.

### `catalog::list.folder_recursive` (33,189,010 Ir, 4,000 rows)

- **Versus `all_name`:** +1.9 M (+6.1%) for the same 4,000 rows. The count query grows from 0.6 M to 1.6 M, and the
  `order_key` range scan grows by about 0.9 M.
- **Inferred:** the extra cost is the upper bound on the range (`order_key < ?`), which adds a per-row comparison that
  the open-ended `all_name` range doesn't pay. The bound was not removed to confirm this.
- **Bench target: confirmed.** The bench's scope is the library root, recursive. The catalog has one root, and it
  contains all 80 folders, so the bench returns every file and never tests a real subset. Pointing it at a folder with
  subfolders would fix that.
- **Folder count: resolved.** The catalog has 80 folders, each with 50 files, and the generator's default is 80
  (`tools/profiling/synthetic_library.py`). The bench comment saying 81 is stale.

### `catalog::pending_import.empty` (116,050 Ir, one idle round)

- **Split:** statement preparation about 106 K (91.5%), transaction begin and commit 5.9 K (5.1%), execution 5.2 K
  (4.5%), locks under 1.5%.
- **Per round:** two statements (`count(*)` and the pending list) are prepared fresh on each call. That is the round's
  cost.
- **Per file:** nothing is measured. The catalog is empty, so the row loop never runs.
- **Suggestion (low value):** `prepare_cached` for the two statements. **Checked:** the app keeps one connection
  between rounds (`crates/library/src/runner.rs`, the job's `round`), so a cache would persist there. The saving is about
  0.1 M Ir per round, small against the roughly 70 M Ir one image's analysis costs. The bench would need a warm-up call
  in setup to show it.
- **Call counts:** see `list.all_name` and open question 1.

### `catalog::pending_thumbs.at_height` (47,056,271 Ir, one check over 4,000 files)

- **Split:** the pending query is 43.6 M (92.5%). Of that, B-tree seeks dominate: one `analysis` lookup and one
  `entries(file_id, height)` probe per file (4,001 index seeks), and 20,002 table seeks from the scalar subqueries.
- **Cursors:** 12,012 opened and freed, about 3 per file, 4.3 M (9.2%).
- **Mutexes:** 64 K lock/unlock pairs, 3.1 M (6.5%).
- **Connection overhead: confirmed in code.** `pending_in` (`crates/thumbcache/src/lib.rs`) calls `Connection::open` on
  every call, then `ATTACH`es the catalog and sets `PRAGMA cache_size = -131072`. The 3.5 M (7.5%) is therefore
  structural to the call, and each call starts with a cold page cache.
- **Only the full-scan path is measured: confirmed.** The bench layout's `thumbs.sqlite` has 0 rows in `checked` and
  4,000 in `entries`, so every round takes `SCAN f USING INDEX sqlite_autoindex_files_1`. After a full pass the app
  writes `checked`, and later rounds use the `since_checked` branch of `pending_sql` (`f.seq > ?2`, reading only changed
  files). That path is never measured, and it is **inferred** to be much cheaper.
- **Suggestion:** add a steady-state variant to `crates/bench/benches/ir/catalog.rs`. Setup would write a `checked` row
  in the run copy, outside the measurement, so the cheaper branch is exercised. This is a gap in the measurement, not a
  regression.
- **Page reads: cause found.** `readDbPage` runs 1,799 times, against 994 pages in the layout. The cause is the attached
  catalog's default cache (2,000 KiB) while `pending_in` sets the cache only on the main connection. With
  `PRAGMA cat.cache_size` set, the cache misses fall from 1,792 to 698 in the instrumented run. See open question 7.

### `catalog::tree.all` (3,457,473 Ir, `folder_tree` over the whole catalog)

- **Split:** libsqlite3 71.4%, `pg_model` 12.2% (path and tree building), std 9.1%, libc 5.9%.
- **Per file:** the folder-count query (`FOLDER_COUNTS`) is 2.2 M (63%), about 545 Ir per file, a covering-index scan of
  `files_present` with a `GROUP BY` and a correlated folder-path lookup per folder.
- **Per folder:** the Rust side (`TreeBuilder::add`, `push_folder_key`) is about 910 K (26%), about 11 K Ir per folder.
  Folder keys use per-character Unicode casefolding.
- **Allocation:** about 6,200 mallocs, about 4% of the total.
- **Seeks: profile artifact, likely.** `sqlite3BtreeTableMoveto` runs 7,553 times in the profile, where the plan
  predicts about 80 (see open question 6). The body's own work is 31,480 VDBE opcodes, with `FOLDER_COUNTS` at 30,261.
  `countStep` at 3.9 calls per file is not checked against runtime.
- **Suggestion:** no action indicated.

### `per_file::analyze_jpeg.sample` (69,821,436 Ir, one `Analyzer::analyze`)

- **Split (measured inclusive, mutually exclusive):** decode `decode_into` 32.4%; resize (both `fit_within` calls, PDQ
  at 512 px and ThumbHash at 100 px) 30.2%; PDQ hash 29.5%; ThumbHash encode 6.4%; content hashing (xxh3 plus BLAKE3)
  1.6%.
- **Per pixel:** about 53.6 Ir per source pixel. The decoder is 16.6 Ir per source pixel.
- **PDQ row pass: premise confirmed by file-level attribution.** `box_1d`, `box_columns` and `dct_64_to_16` are not
  separate symbols; they are inlined into `dct16`, and callgrind attributes their lines to the core library files. Inside
  `dct16`, the self cost is 5.2 M in `pdq.rs`, and in iterator adapter code: `take` 8.3 M, `skip` 2.5 M, slice iterators
  2.3 M and `zip` 0.8 M. The per-element `take` and `skip` calls are only in `box_1d` (**inferred**: the other passes do
  not call them per element), so the row pass carries most of the adapter cost. `box_columns` costs about 1 M, as stated.
- **Proposed fix:** rewrite the row pass as indexed loops in the same arithmetic order. **Checked:** this keeps results
  bit-exact (the same `f32` operations in the same order; Rust does not reassociate floats). **Measured:** in the WSL
  clone, `analyze_jpeg.sample` went from 69,821,436 to 64,405,148 Ir (−5.4 M, −7.8%), below the 8–10 M estimate. The
  three PDQ tests pass, including `columns_at_once_change_no_bit` and `matches_reference_crate`. The bounds checks cost
  less than the iterator adapters saved. The working tree has uncommitted cast-only edits to
  that file, so a change must merge with them.
- **Lanczos coefficients: corrected.** `precompute_coefficients` runs when a coefficient key misses, not on every
  resize. The vendored `fast_image_resize` already caches the last key of each axis (`vendor/fast_image_resize/src/resizer.rs`,
  `AxisCoefficients`; present at 1bb0390). The real gap is in `analyze.rs`: one `Resizer` does the 512 px PDQ resize
  (`analyze_image`) and then the 100 px ThumbHash resize (`thumbhash`). Each resize evicts the other's coefficients, so
  neither hits the cache, on any image. Production keeps one `Analyzer` per import worker (`crates/import/src/lib.rs`), so
  this applies to every image. A separate `Resizer` for the ThumbHash path is bit-exact. Its saving appears only on
  consecutive images of the same source size: 3.3 M of 69.8 M here, about 4.7%. The cold bench cannot show it.
- **Memset:** 3.6 M, mostly buffer-growth zeroing on a cold first file (the bench builds the `Analyzer` in setup, so the
  body is always a first file). **Inferred:** a warm worker would skip most of it. Callgrind may also count each
  `rep stos` iteration, which overstates memset time.
- **Unresolved:** `blake3_hash_many_avx2` (311 K) and `blake3_compress_in_place_sse41` (3 K). See "Unresolved symbols".

### `per_file::thumb_jpeg.h256` (52,272,812 Ir, one `Maker::make` at 256 px)

- **Split:** decode (libjpeg-turbo) 55.7%, resize (`fast_image_resize`) 39.1%, encode 5.2%. Libjpeg-turbo is linked
  statically into the bench binary via `turbojpeg-sys`.
- **Hot functions:** Huffman decode (`decode_mcu`) 23%, vertical resize convolution 18%, IDCT (`jsimd_idct_islow`) 14%,
  horizontal resize 11%.
- **Per pixel:** about 40 Ir per input pixel (1280×1017) and about 630 per output pixel. **Inferred** pixel counts from
  call counts.
- **Lanczos coefficients:** `precompute` 3.3 M (6.2%), with 27,420 `sin` calls. The same caching note as `analyze_jpeg`
  applies: a single cold resize computes them once.
- **Nothing redundant:** one decode, one resize and one compress per call.
- **Decode scale: resolved, no conflict.** The thumbnail path uses `MinSize::Upright(0, 4 × 256 = 1024)`
  (`crates/render/src/maker.rs`). The sample's 1017 px height is below 1024, so the scale is 1: a full-size decode. The
  `analyze` path uses `MinSize::Sides(512, 320)`, which gives a 1/2 scale and a 640×509 decode. The two drills were
  reading different minimums, and both were right.
- **Production case not measured:** a 12 MP photo (4032×3024) is 3024 px tall, so its 256 px thumbnail takes the 1/2
  scale (1512 ≥ 1024; at 1/4 it would be 756, below the minimum). The bench's sample never takes that path. The 56%
  decode share describes full-size decoding, not the common production case. See Recommendations.

## Cross-cutting findings

1. **SQLite dominates the catalog benches.** It is 71–92% of the instructions in each catalog profile. The Rust code
   around it is a few percent. Improvements in the catalog benches are mostly about SQL shape and statement reuse.
2. **Statement preparation is a fixed cost in several benches,** but a small one in absolute terms: about 0.1–0.3 M Ir
   per call for `pending_import` and `folder_flat`. Several statements are prepared fresh on every call (`list_grid`,
   `facets`, `pending_import`). Whether `prepare_cached` pays depends on how the benches create catalogs; the benches
   currently create one per iteration.
3. **The fixture does not exercise several code paths. Corrected causes:**
   - `ratings` is empty because the generator writes no ratings, and `bench_data.py` inserts none.
   - `border_marks` and `border_sides` are empty, and `analysis.cut_*` is NULL for every file, because the borders pass
     never ran on the bench layout (3,795 analyses still have `borders_due = 1`; the other 205 are presumably the
     ineligible videos, animations and tiny images, not checked). Whether the synthetic images would produce borders at
     all is not known: they are smooth gradients.
   - `analysis.taken` is NULL for every file because the generator writes EXIF `DateTime` (0x0132) in IFD0, and the
     reader takes `DateTimeOriginal` (0x9003) or `DateTimeDigitized` (0x9004) from the Exif sub-IFD (0x8769). The
     synthetic files therefore have dates the reader never sees.
   - `checked` is empty, so only the full-scan branch of `pending_thumbs` runs; the steady-state `since_checked` branch
     is never measured.
   - The image benches decode the 1280×1017 sample at full size for thumbnails; production photos decode at 1/2 scale.
   - `folder_recursive` covers the whole library, so it never tests a subset (confirmed).
4. **Measured costs that look like redundant work, but are small:** the `count(*)` pass that sizes each list
   (1.9–4.9%), repeated Lanczos coefficient computation (4.8–6.2% in the two image benches, and only on a cache miss,
   which the shared `Resizer` causes), and the per-call `sqlite3_free` volume (under 0.3%).
5. **The archive is mostly decodable on its own.** Named functions are stored in the `.out` files (for example
   `<pg_analysis::pdq::Hasher>::dct16`). Only address-only entries need the binary's symbols, and those are 0.09% of Ir
   (see below).

## Recommendations

1. **Do not store the symbol table with the archive, for now.** The unresolved share is 0.09%, and the archive is decodable
   for the rest. Revisit only if a profile's address-only entries start to matter.
2. **Measure the steady-state paths.**
   - `pending_thumbs`: in setup, write a `checked` row into the run copy, so the `since_checked` branch is measured.
   - Image benches: add a production-size sample (a 12 MP photo, which takes the 1/2 scale for a 256 px thumbnail), so
     the decode path measured is the common one.
3. **Fix the fixture at the source, not by hand.**
   - Dates: make `tools/profiling/synthetic_library.py` write `DateTimeOriginal` in the Exif sub-IFD (tag 0x8769), not
     only `DateTime` in IFD0, then regenerate the library and the bench layout. **Verified through an import** (WSL,
     8-file library): with the current generator, `analysis.taken` is NULL for all 8 files. With the patch, all 4 JPEGs
     get a `taken` that matches the EXIF date in the file. PNGs and WebPs carry no EXIF from the generator, so their
     `taken` stays NULL. The bench layout still has to be regenerated.
   - Borders: run the borders pass when building the bench layout (`tools/profiling/bench_data.py`), and give some
     synthetic images a bar or letterbox, since smooth gradients may produce no borders at all. Without this, the
     `border_sides` hit path stays unmeasured. **Verified:** the `borders` command on the unpatched generator's 8 files
     finds 0 borders (every cut is 0, so `border_sides` is empty). With a letterbox on half the JPEGs, one of four
     JPEGs gets two `black` rows, with 41 px cut at top and bottom, so the hit path runs. `bench_data.py` does not run
     the borders pass yet; this is not changed or run.
   - Ratings: have the generator or `bench_data.py` insert rows in `ratings`. The table is in the catalog, so this does
     not need a file-level change.
4. **Decide the caching question before changing code.** If `prepare_cached` is adopted, warm the cache in the bench's
   setup. Otherwise the bench shows no gain, because it opens a new `Catalog` every iteration. Given the size of the
   saving, the change is low priority.

## Open questions

1. **Prepare call counts: body count confirmed, profile count not reproduced.** An instrumented copy of rusqlite (a
   counter at the top of `InnerConnection::prepare`, in the WSL bench clone at `1bb0390`, not the repo) counted the
   prepares that each catalog call makes at runtime: `list_grid` makes 4 (its count, its grid statement, `BEGIN` and
   `COMMIT`), `facets` makes 5, and `pending_import` makes 4, on 4,000 rows. That matches the source. The callgrind
   figure of 24 is therefore not the number of prepares the body makes. Its call counts (17 and 7) do not reconcile with
   the runtime count, and the profile has no setup function names to account for the difference. Most likely a call
   attribution artifact in the profile, not extra work in the code. The prepare Ir is still real (about 267 K in
   `folder_flat`), it just comes from 4 prepares, not 24.
2. **Decode scale for the 1280×1017 sample: resolved.** Two different minimums (see `thumb_jpeg`).
3. **Folder count: resolved.** 80. The bench comment saying 81 needs correcting.
4. **`folder_recursive` coverage: resolved.** It covers the whole library (all 80 folders, 4,000 files).
5. **`pending_in` connection per call: resolved.** It opens a connection on every call, with an `ATTACH` and a 128 MB
   cache setting, so the 3.5 M is structural.
6. **Unexplained seeks: resolved as a profile artifact (likely, not proven).** Runtime counts from an instrumented clone
   (per-statement VDBE opcodes from `sqlite3_stmt_status`, run through the bench's own calls) show the body's real work:
   - `folder_flat`: 3,288 opcodes in total. The grid runs 3,118 for 50 rows (about 62 per row); the count runs 164.
   - `tree.all`: 31,480 opcodes. `FOLDER_COUNTS` runs 30,261 for 4,000 files, with 3,999 full-scan steps.

   The profile's table-seek counts do not fit that work. `folder_flat` shows 7,623 table seeks (`sqlite3BtreeTableMoveto`)
   under `sqlite3VdbeExec`, more than the body's 3,288 opcodes in total, and the reconstructed plan predicts about 250
   (about 4 table seeks per returned row). `tree.all` shows 7,553, where the plan predicts about 80 (correlated lookups
   into `folders`, one per folder). The same profile also overstates the body's own rusqlite calls: `execute_batch` 7
   against 2 at runtime (`BEGIN` and `COMMIT`), `get_expected_row` 14 against 1, `sqlite3_step` 72 against about 54, and
   `sqlite3_prepare_v3` 24 against 4 (question 1). The `pending_thumbs` seek counts (20,002) are from the same kind of
   count and are not checked. The measured Ir is not derived from these counts, so the Ir figures stand. The seek figures
   should not be read as the code's table-seek work. Not proven: the cause inside callgrind's call counting is not
   identified.
7. **Page reads: resolved, cause found.** The layout's files total 994 pages (`catalog.sqlite` 916 and `thumbs.sqlite` 78,
   at 4,096 bytes each), confirmed with `PRAGMA page_count`. In the instrumented run, `pending_thumbs` causes 1,792 cache
   misses (`sqlite3_db_status` `CACHE_MISS` on its connection), against 1,799 `readDbPage` calls in callgrind. About 800
   of those are repeats. The cause: `pending_in` sets `PRAGMA cache_size = -131072` on the main connection only. The
   catalog is attached as `cat` without that setting, so it keeps SQLite's default cache (2,000 KiB, about 500 pages).
   The catalog has 916 pages, and the pending query scans it, so pages are evicted and read again. Test: adding
   `PRAGMA cat.cache_size = -131072;` after the `ATTACH` in the clone cut the misses from 1,792 to 698. The fix is not in
   the repo. The saving in Ir is not measured.
