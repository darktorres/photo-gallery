# Plan: mount-point roots, a stored root volume, waiting roots, and the shell's start folder (D-061)

Claims are marked **verified** (run on this machine, or read in the code) or **predicted** (reasoned; the check that confirms it is named). Nothing here touches the owner's real catalog (`D:\PhotoGallery`): every run uses scratch folders and scratch catalogs.

## Context

D-061 asked whether the three drive-or-share predicates should be one. Reading the path, dialog, volume and scanner code, and testing on a real mount, turned it into one change with five parts.

What is true today:

- **Links already work.** `add_folder` runs `normalize_path` (`canonicalize`, then the verbatim prefix is dropped) before `check_folder`, so a junction or symbolic link is resolved to its target first. A junction to `D:\a\pg_trace_cat` was added as `D:\a\pg_trace_cat` (verified). That covers roots only. A link *inside* a root is not followed today: the walk skips every reparse folder and keeps a reparse file's row without reading it (verified, `lib.rs` ~1085-1100). Decision 10 changes that (work package 8).
- **A mount point is the one link that survives resolution.** `canonicalize` gives the mount folder itself (`D:\a`), and `check_ntfs` step 4 refuses it as "a link (a junction or a symbolic link)", which is the wrong reason (verified with the CLI). Steps 2 and 3 pass first, so the drive-type check already sees the mounted disk (verified by that refusal order). A folder *inside* a mount is accepted and stored as `D:\a\…` (verified).
- **That holds for a disk without a drive letter.** With both a letter and a mount folder, `canonicalize("D:\a")` is predicted to answer `F:\`, and the add would store `F:\` (check 2 below).
- **A disk that leaves a mount folder can leave an empty plain folder.** `D:\mounted disk` stayed behind; `D:\a` was removed (both verified). A scan of the empty folder would mark the root's files missing. That is reversible ("back from missing"): the missing mark only sets `missing = 1` and keeps `volume` and `file_ref`; the statement that clears them (`writers.rs:163`) runs only when another file takes over the identity (verified). The check prevents churn, not a loss.
- **The mount is gone now.** The owner put the disk back on `F:`; `D:\a` and `D:\mounted disk` do not exist (verified).
- **Reproduced on Linux, end to end, today's headless `gallery` (container, root with the capability):** a root that is a tmpfs mount is scanned (2 files, volume recorded); after unmounting, the same root is scanned again and **both files are marked missing, with exit 0**. So the WP4 defect is not Windows-only, and the Linux side of the check is needed. A nested tmpfs inside a plain root is walked today, and its file records a different volume from the root's own files, so the Linux walk already crosses nested mounts.
- **The catalog's schema can still be edited in place.** `MIGRATIONS` is empty and `schema.rs` says "before the first release the baseline is edited in place" (verified).

Owner decisions:

1. A root that resolves to a local, fixed, NTFS volume is allowed, a mount point included.
2. A root records the volume it is on, and a scan refuses a root that is no longer on it, so an unmounted mount point makes the root wait instead of marking its files missing.
3. The start folder from the environment goes through the same shell checks as every other start folder; if it fails them, the dialog opens with no start folder and no error.
4. The CLI exits non-zero when any requested root was not added or scanned.
5. A refusal met while scanning is worded "can't be scanned". The no-arg scan already scans the stored roots directly (`catalog.roots()`, `cli/src/lib.rs:304`); only the wording changes.
6. A verbatim volume path (`\\?\Volume{GUID}\…`) is an anchor of its own, and other verbatim or device forms are rejected explicitly. A path model should represent a form correctly or reject it, and normalization must not change a path's meaning.
7. Waiting roots are three states, built now, on Windows and Linux: volume absent (waits), folder gone from a present volume (an error), root changed volume (waits).
8. Cloud-sync folders (reparse folders that resolve to themselves, such as the user's `Dropbox`, tag 0x9000F01A) stay refused, with a sentence that names them.
9. `form_of` stays as it is: a verbatim volume path already opens (verified: `std::fs::metadata` and `read_dir` open `\\?\Volume{…}\` and its folders).
10. Links are allowed wherever they appear, as long as they point to NTFS: a junction, symbolic link or mount point inside a root is followed when its target passes the checks a root passes (local, fixed, NTFS; on Linux, an allowed file system), folders and files alike. A link whose target is refused is recorded and skipped; a cloud-sync placeholder (it resolves to itself) stays unfollowed. (The owner's earlier instruction: "we should allow links as long that they point to NTFS". An earlier draft applied it to roots only and called nested links a boundary; that was wrong.)

Known limits, kept on purpose: a disk remounted at a different folder breaks its stored root (roots are stored by path; re-keying a root is a separate feature, and the stored volume makes it possible later); a reformatted, cloned or restored disk has a new volume identity, so its root waits until the user accepts the new disk (work packages 4, 5 and 7). That action is required, not optional: the pairing rebinds files by folder, name, size and mtime across volumes (tier 1 in `catalog/src/pair.rs`, verified) and keeps their ratings, so a cloned disk works today; the only other way out of the wait, removing the root, deletes its files' ratings and analyses; a root on a volume with no stable identity (Linux without a UUID) has no volume check and no changed-volume state, and the pairing keeps handling a renumbered volume as it does today; a volume path is never stored, since a root needs a drive letter or a mount folder; a followed link whose target is later unplugged leaves its rows unresolved (kept, listed in the failed folders), and a link removed from the listing makes its files missing, as any deleted folder does.

### 2. The volume anchor (`model/src/rules.rs`, `platform/src/names.rs`, `scan/src/refusal.rs`)

- Defect (verified in `parse_bytes` and `join`): `without_verbatim` turns `\\?\Volume{G}\x` into `Volume{G}\x`, which parses as a relative path and joins as the rooted text `\Volume{G}\x`: an absolute path silently changes meaning.
- **Reach, measured on this machine (an earlier draft had this wrong).** `canonicalize` is `GetFinalPathNameByHandle` with DOS names. For a GUID path to a volume with a drive letter it answers the drive form (`\\?\F:\pg_trace_cat`), and for a letterless volume it **fails** (error 3), so a typed volume root is refused as unreadable before `without_verbatim` runs and the add never sees a volume path. The defect is reached only through `rule_path_in` on a typed path that is not canonicalized: `real_path_lenient`'s fallback when nothing of the path exists (a volume that is not present; callers: the CLI `remove`, crop's output folder), and the Yandex save folder (from a dialog, so the drive form). So the step changes no behavior a user can reach except the words of an error for a typed volume path of an absent volume. It stands as the owner decided, for the model's correctness. **Recommendation, on this evidence:** reject instead of represent (`rule_path_in` returns `None` for a volume path, so it is `NotAPath`, and the anchor, the `drive_letter()` rewrite, the rules-docs rewrite and the `check_ntfs` narrowing are not built); the principle (represent or reject) is met by the smaller choice for a form that can neither be stored nor produced. Until the owner says so, the plan keeps the anchor.
- `parse_bytes` reads `\\?\Volume{<guid>}` (GUID-shaped, hex in either case) as the anchor and the rest as parts. `join` is unchanged; `path_key` already lowers the anchor, so one GUID in two cases is one key; `is_under` and `same_anchor` compare it by the same rule. A name that is not GUID-shaped parses as today. `drive_letter()` is rewritten to read only a drive anchor (`X:`). Today it drops every `:` and `\` from any anchor and answers the rest, so a volume anchor would answer `?Volume{G}` and crop (`crates/crop/src/lib.rs:148`, its one consumer) would build a folder of that name (verified in the code). `tree.rs:126` already treats every anchor but a drive as none (verified), and `display` writes anchor, separator and parts, so a volume path displays right.
- `without_verbatim` strips only `\\?\X:\` and `\\?\UNC\`, and keeps every other form as it is, so it never changes a path's meaning. The explicit rejection is made where a path becomes a rules path (`normalize_path` and `rule_path_in`): a verbatim or device form that is not a volume path (`\\?\GLOBALROOT\…`, `\\?\pipe\…`, `\\.\…`) is `NormalizeError::NotAPath`. `shown` (display) keeps showing such a path as typed, since a display must show something.
- `check_ntfs` step 1 treats only UNC forms (`\\server`, `\\?\UNC\`) as network paths. A volume path flows on and is refused as `RealNotLocal` (`local_drive_path` needs a drive letter).
- Rewrite the rules' docs to match (`rules.rs` lines 1-5, 15, 90-95, 291-292). A drive spelling and a volume spelling of one folder stay two keys (not folded), now as two anchors.
- Tests, pure in `model` (they run on Linux): parse, `join`, `path_key`, `is_under`, `drive_letter` and display of a volume path; case folding of the anchor; a malformed GUID. On Windows: `without_verbatim` on each form and the `NotAPath` cases; `check_ntfs` on a volume path (`RealNotLocal`, not `NetworkPath`).

### 3. Mount points in the scanner (`scan/src/refusal.rs`, `platform/src/dir.rs`)

The call succeeds on a volume root (`F:\` gave its GUID) and fails on a junction (87), a plain folder (4390) and a cloud-sync folder (123) (all verified). On a mount folder it is predicted to succeed (check 1). Fallback if it does not: the folder is a mount when `volume_root(path)` is the path itself (`GetVolumePathNameW` follows a junction, verified: the scratch junction on C: answers `D:\`).

The earlier NTFS probe could not tell, since D: and F: are both NTFS. `file_system` takes the volume root already computed in step 5 (`GetVolumeInformationW`) for every folder; for a plain folder the answer is the same. Predicted from the code; confirmed by check 6. `RootFacts::file_system` has two callers (`refusal.rs:61`, `dir.rs:850`).

- Tests, with the fake extended (its `volume_root` is the first three characters of the path and its file system one flag, so it cannot model a mount today): a mount root, a file system per volume root, `is_volume_root` as a flag. ### 4. The root's volume, and the check that uses it (`catalog`, `scan`)

- **Schema (in place):** `roots` gains `volume INTEGER` (nullable), stored as the SQL integer of the identity's bits like `files.volume` (`identity_to_sql`). `baseline.sql` is edited in place, as `schema.rs` allows before the first release. NULL means "not recorded": a root added before this change, or one whose volume could not be read.
- **What the edit does to an existing catalog** (verified in `core.rs` `prepare` and `rebuild.rs`): any catalog made from the old baseline is rebuilt on first open. A new file is made in the new layout, the rows are carried by column name (`carry_rows`; a column the old file lacks takes its default), and the old file is moved aside and kept beside it. So a **nullable** `roots.volume` carries with NULL, while a column the new layout needs and the old lacks would fail the copy and leave an empty catalog. The new `root_volumes` table (work package 8) goes in `CARRIED` (`rebuild.rs`: every table is there or in `TRANSIENT`, none is derived), after `roots`. This includes the owner's real catalog the first time a build with this change opens it (the old file stays beside it as the backup). A test prepares a catalog from the old baseline (`Prepare::schemas`, as the existing rebuild tests do) and checks its roots carry with a NULL volume.
- **Only a stable identity is recorded or compared.** On Linux `volume_id` (`dir.rs` ~677) returns `None` for a volume with no UUID, and the walk then uses the device number, which a restart can renumber (the code says so, and `ScanNote::VolumeFallback` counts it). Verified in the `pg-dev` container (Linux 7.0, no udev data): the kernel's `FS_IOC_GETFSUUID` answers a 16-byte UUID for overlayfs, tmpfs and ext4, and only procfs answers none. So from kernel 6.13 almost every allowed volume is stable; the unstable case is an older kernel with no udev record, or a file system that has no UUID (an NTFS driver, for one). Today a renumbered volume is handled by the pairing ("files found again"). A check that recorded the device number would call every such root `Changed` after a restart and refuse its scans for good. So: the new `Listing::stable_volume(&dir) -> io::Result<Option<u64>>` answers the file-system identity (a UUID or serial; always `Some` on Windows, where it is `FileIdInfo`'s serial) or `None` when the walk would use a device number; the fake has a `stable` field. `Listing` has three implementors to update: `Lister`, the test `FakeListing` and the bench `SyntheticTree` (`synthetic.rs`). A root on a volume with no stable identity records nothing and has no check and no changed-volume state; the pairing keeps handling it. This is a stated limit, and it is the only way the check stays correct. **Found in the container:** the fallback note is counted for a **refused** nested mount with no UUID too (a devpts mount inside a root produced "1 volumes have no file system UUID" for the root, which was the mount's device). The count must leave out refused mounts, or the note misleads; the implementation fixes that.
- **API:** `Catalog::add_root_on(root, volume: Option<u64>)` is the one production way to add a root. `add_root(root)` stays only as a test helper (`add_root_on(root, None)`, `#[cfg(test)]`/the testing feature), so a production add always passes what it read. `Root` gains `volume: Option<u64>`. A new `Catalog::set_root_volume(root_id, Option<u64>)`, used by the scan's recording of a NULL volume and by the user's acceptance of a new disk (below). NULL means a legacy root, or one on a volume with no stable identity.
- **Accepting a new disk.** A root that is `Changed` is not a dead end: `pg_library::folders::accept_volume(catalog, root)` reads the root's current stable volume and sets it, and the next scan then runs and the pairing rebinds the files (tier 1 and 2, `catalog/src/pair.rs`). It is the user's explicit act, offered by the Library panel (work package 7) and the CLI (work package 5), and the wording warns that files not found on the new disk are marked missing (the case of an unmounted mount point whose empty folder is accepted by mistake; they come back when the disk does). It refuses a root with no stable current volume.
- **When it is set.** `add_folder` reads `pg_scan::stable_volume(rules, root)` after `check_folder` passes and adds the root on it (`None` stores NULL). A scan that finds NULL and a stable current volume records it (below).
- **The rule, in one place.** `pg_scan::volume_verdict(stored: Option<u64>, current: Option<u64>)` (both stable identities): equal is `Same`; both present and different is `Changed`; a missing stored volume is `Unrecorded`; a missing current volume (no stable identity now, or udev not ready) is `Unknown`, and no check is made, since the check only protects. The scan uses it, and so does the app's root state (work package 7), so there is one definition.
- **Where it runs.** In `walk_paced`, after `root_volume` is computed and before `begin_scan`: nothing is written when it fires (no scans row, no missing marks), and the existing fake listing (its `root_volume` is a field) can drive it (verified in the code). **It runs only when the walked folder is a library root** (found by exact path with `Catalog::root_id(path)`, which exists, and `roots()` for its volume). The runner also queues scans of a folder under a root (the test `only_a_walk_of_the_whole_library_folder_replaces_its_conditions` queues a root and a subfolder), and a subfolder's own volume can differ from the root's once links are followed (work package 8), so a subfolder walk is not compared. A subfolder that is gone fails to open before any write.
- **`Unrecorded`** is a legacy root. Its volume is taken from its files once, by a small catalog method over the folders in the root's `PathRules::subtree` key range (`folders.path_key` is `UNIQUE`, verified) joined to `files` by `folder_id` (index `files_folder`): two `EXISTS` probes, any non-null volume and one equal to the current volume. Files and none on the current volume: `Changed`. Otherwise the current volume is recorded and the scan goes on. After that the files are never consulted again, and a root with no files is protected from its first scan.
- **How it reaches the user.** `Changed` returns `ScanError::Refused(RefusedReason::VolumeChanged)`, and `scan()` records the ledger row for any `Refused`, the walk's included (`folder_refused`, `ctl.ledger_changed`), as it does for `check_folder`. The ledger stores the reason as data, not as `reason.to_string()` (its key), so the app can word it in the reader's language (work package 7). The conversion is `RefusedReason::to_stored()` and `from_stored(&str)` in `model` (serde and `serde_json` are `model` dependencies; `scan` and `library` have no serde at all, and `client` depends on `model` alone, verified in the manifests and `tools/crate-layers.txt`), so no crate gains a dependency; a stored text that does not parse is shown as it is. Two places read a ledger row's text (verified): the Copy line (`desktop/src/notices.rs` ~205) and the failed-files panel's model (`desktop/src/failed_files.rs:77`, whose `ROLE_ERROR` shows `folder.error` raw); both word it through one function in `client` (work package 7). `passes.rs` already treats `Refused` as "recorded, wait", and the CLI prints it. It does not go through the lanes: `probe_place` never sees a `ScanError`, and a folder that exists answers `Mounted` (verified in `lanes.rs` and `coordinator.rs`).
- **When it fires.** For a root that is itself the mount folder, or a drive letter given to another disk that has the same path. A root inside a mount is a missing folder once the mount is gone, which is the "volume absent" state in work package 7.
- Lands with work package 5, because until then the CLI words this refusal with the add notice.
- Tests (fake listing, in-memory catalog): a root recorded on A and walked as B is refused, with nothing written, nothing marked missing and no scans row; A then A proceeds; a root with no files is refused too; a NULL root with files only on A, walked as B, is refused; a NULL root with no files records the volume; a root recorded on A and walked on a volume with no stable identity is not refused (`Unknown`); a walk on such a volume records nothing; `add_folder` records the volume and records NULL for an unstable one; the ledger row round-trips the reason (`to_stored`/`from_stored`, and an unknown or old text reads as `None`); `accept_volume` records the current volume and the next walk proceeds, refuses a root on an unstable volume, and a walk as B after accepting, over files recorded on A with ratings, pairs them to the new rows (tier 1) and keeps the ratings. Rows marked missing still count for the backfill.

### 7. Waiting roots in the app (`platform`, `library`, `jobs`, `app`, `client`, `desktop`)

The edits:

- **`platform`: a `Volumes` trait beside `Drives`** (`drive/types.rs`), `fn mounted(&self) -> io::Result<Vec<MountedVolume>>` with `MountedVolume { identity: u64, paths: Vec<PathBuf> }`, and `SystemVolumes`.

- **`library`: the state.** In `lanes.rs`, a pure `root_state(facts) -> RootState`:
  - Facts: how `root_volume` answered (a volume, NotFound, or another error), the root's current stable identity, its recorded volume, the mounted volumes, and, for a NotFound, whether the root's drive root exists. "NotFound" in this list means the lanes' own test, `platform::drive::unplugged` (verified in `drive.rs`): the NotFound kind, Windows `ERROR_NOT_READY` (a drive with no media in it), or Linux `ENODEV`/`ENXIO`. A not-ready answer is `Absent` without asking the mounted list (the device is there with nothing in it); `Gone` needs a real NotFound with the recorded volume mounted. The mounted volumes are listed **only when the root answered NotFound**: the listing costs a handle on every volume's root, which would otherwise touch removable and optical drives every 15 s for every root for nothing. If the listing fails, the state is `Unknown`, never `Absent`. **The place is answered first.** A probe that has not answered within `PROBE_DEADLINE` (5 s) makes its root `Place::Unknown`, and one `Unknown` root puts every other root in one lane (`lanes::plan`, verified), so a slow volume listing (opening the root of a sleeping disk can take seconds) would flip the whole lane plan. The probe thread therefore publishes the place first, then computes the state and publishes it as a second answer with its own deadline; a state that is late stays `Unknown` and never touches the place.
  - `Present`: it answered and the verdict is `Same`, `Unrecorded` or `Unknown`.
  - `ChangedVolume`: it answered and the verdict is `Changed`. Waits.
  - `Absent { label }`: NotFound and no mounted volume has the recorded identity (with none recorded, a drive letter whose root does not exist). Waits. `label` is the drive letter when the root's anchor is a drive whose root is missing, else none.
  - `Gone { now_at }`: NotFound and the recorded volume is mounted. An error the user can restore or remove. `now_at` is a path of that volume when the root's own path is not under any of them, so "it is mounted at X now" can be said.
  - `Unknown`: any other error, as `Place::Unknown` is today; no note is shown.
  - **A waiting root is out of the lanes, not just out of the scans.** The lane plan leaves out only `Place::Unplugged` roots ("an unplugged root has none at all", `lanes::plan`); a root with a `Mounted` place gets a lane that runs all seven passes (scans, import, hashes, pairing, borders, thumbs, placeholders) over its files. For a `ChangedVolume` root (an empty folder on the parent volume) that is wasted work against files that cannot be found. So `probe_place` returns `Place::Unplugged` for `ChangedVolume` as well, and the root has no lane until it is back. The scan guard of work package 4 stays for the CLI and for a race.
  - `probe_place` takes the recorded volume and a `&dyn Volumes`, and returns the place with the state; the probe thread (`spawn_probe`) is given the recorded volume from `conn.roots()`. ### 8. Links inside a root (`scan`, `platform`, `catalog`, `library`)

Decision 10: junctions, symbolic links and mount points inside a root are followed when their target passes the checks a root passes; cloud placeholders and links with a refused target stay unfollowed and are recorded.

What exists (verified): the Windows listing flags a reparse entry (`FILE_ATTRIBUTE_REPARSE_POINT`, `dir.rs:540`) and sets `Entry.device` to `None` (one volume per folder); the walk skips every reparse folder (`SkipReason::Reparse`) and keeps a reparse file's row unread; Linux flags symlinks the same way (`is_symlink`), and Linux nested mounts are already walked through `other_device`, `volume_of_device` and `check_mount`; a `Job` carries `path`, `device`, `volume` and `chain`; `FolderFailure` has `Unreadable`, `MountRefused` and `Refused`; a lane's volume set is built from its roots' own volumes (`lane_volumes`) and `pending_import` filters files by it.

Design:

- **Classify a reparse entry by its reparse tag, a whitelist, read from the listing itself.** A directory record's `EaSize` holds the reparse tag when the reparse attribute is set (`FILE_ID_BOTH_DIR_INFO`). Verified on this machine with no per-entry open: the profile's junctions report `0xA0000003`, and the Dropbox cloud folders `0x9000F01A`, `0x9000E01A` and `0x9000601A`. So `Entry` (`platform/src/dir.rs`, and the scan's `DirEntry`) gains `reparse_tag: u32` (0 for a non-reparse entry, and on Unix), and the workers stay stateless. A tag that is not on the whitelist is skipped with no open at all, which matters in a cloud folder with tens of thousands of placeholders; only a whitelisted entry is followed, in the walk's consumer thread, with one open (`Listing::follow(link)`):
  - tag `IO_REPARSE_TAG_SYMLINK` (0xA000000C: verified from a listing of `C:\Program Files\Microsoft Office\root\Client`, whose `C2R32.dll` and others are file symlinks; the listing reports `EndOfFile` 0 for a link whose target is 2,244,376 bytes, which is why a file link's row takes its size and mtime from the target): a symbolic link, target = the resolved path;
  - tag `IO_REPARSE_TAG_MOUNT_POINT` (0xA0000003: verified on the scratch junction and the profile's junctions): a junction, or a volume mount. `is_volume_root` (work package 3) tells them apart: a mount's target is its volume, a junction's is the resolved path;
  - every other tag (a cloud-sync placeholder such as the user's `Dropbox` 0x9000F01A, WSL, deduplication, app-execution aliases): not a link, skipped as `Reparse` and counted in the scan note, as today.
  - Not "resolves elsewhere": a path compare is wrong below a followed link, where every entry's real path differs from its walk path, so a placeholder there would look like a link and be followed (fetching over the network). A tag whitelist does not depend on where the entry is.
- **Check the target as a root is checked** (`check_ntfs` on the resolved target; Linux `check_root`). A refused target is recorded in the ledger with a new `FolderFailure::LinkRefused` (key `link-refused`, carrying the `RefusedReason`; an arm in `msg-failed-folder-reason`) and skipped with a new `SkipReason::RefusedLink` (`catalog/src/types.rs`), as a refused mount is. A `RefusedLink` is a failure like `RefusedMount`, not like `Reparse`: its ledger rows below it must be kept, so it joins `Unreadable | RefusedMount` in the "never looked into" test at `catalog/src/roots.rs:416` (a `Reparse` skip is not a failure and its rows are swept). Both are verified in the code.
- **An accepted folder link becomes a job for the link's path.** Its files are recorded under the link's path inside the root, and open through it. Its volume comes from the opened target (`Listing::volume`), and the target directory's `(volume, file id)` is pushed on `chain`, so a link back into an ancestor, or two links to each other, end as loops (`stats.loops`) by the target's identity, not the link entry's own id. The root job's chain is empty today (`walk_leased`: `chain: Vec::new()`), which was harmless while a plain folder cannot loop: seed it with the root's own identity, and refuse a link whose target is an **ancestor of the root** (its subtree contains the root) as a loop, by comparing real paths. Without both, a junction to the root, or to its parent, walks the whole root again, or the whole drive, before the chain catches it. `Listing` gains `dir_identity(&dir)` (the volume and file id of an open folder) for that and for `follow`. The frame is `pooled: false`, so the walk lists it itself, opening the link's path (the system follows it). On Windows nothing else is needed (verified in the walk): entries have no device, a file takes its identity's volume from `job.volume`, and every child folder inherits it (`child_job`), so the target's volume reaches the whole subtree. `descents` (the workers' list-ahead) already leaves out reparse entries, so a worker never takes a link. On Linux an entry's device is the link's own (`lstat`), so `follow` also gives the target's device for the job, and `volume_of_device` maps it as it does for a nested mount.
- **File links** (a symbolic link to a file) follow the same classification and target check. The row takes the target's identity (volume, file id), size and mtime, read with one open of the link. The same file reached twice is one file and a duplicate count, as today. A cloud placeholder file (it resolves to itself) keeps today's treatment.
- **A target that can't be opened later** (its disk unplugged) is `Unreadable` in the ledger, and the rows below it stay unresolved, like any folder the walk could not look into (`roots.rs`: "the subtrees the walk never looked into").
- **Lanes: a root now has files on several volumes.** A root's volume set is its own volume plus the volumes of its followed targets. Each complete walk **of the whole root** (not a walk of a folder under it, which sees part of the root) replaces them in a new `root_volumes(root_id, volume)` table (the baseline is edited in place; `root_id` references `roots(id)` with `ON DELETE CASCADE`, so removing a root, or an add that replaces roots, takes its rows with it: foreign keys are on, `schema.rs`). `Catalog::roots()` returns them with each root, so the coordinator hands them to the probe thread with the recorded volume (`spawn_probe`). `Place::Mounted` carries the root's volumes; the root's `Drive` is the union of their disks (`drive_of_disks` already takes a list), so roots whose disks overlap share a lane (`same_drive`); `lane_volumes` takes the union, so `pending_import` and the other volume-filtered queries reach those files. A target volume that is not mounted adds nothing until it is. The union is computed inside the probe, within the same deadline: a slow extra volume makes its root `Unknown`, as a slow root drive does today. This needs `Volumes` (work package 7) to map a volume to a path and `Drives::of` for its disks. Today a followed Linux nested mount has the same gap; this closes it too.
- The volume check of work package 4 is unchanged: it compares the root's own volume, and its backfill rule ("files under it and none on the current volume") stays right for a root with files on several volumes.
- The scan note `reparse` ("links or placeholders indexed without being followed") now counts only what is not followed; its sentence is reworded in the locale.
- Linux: a symbolic link to a folder or file is followed the same way when its target passes `check_root`; nested mounts keep their `check_mount` path.
- Tests (fake listing, in-memory catalog): a junction or symlink to a good target is followed, with files recorded under the link's path and the target's volume; a link to a refused target is `LinkRefused` and skipped; a cloud placeholder stays skipped; a cycle (A to B to A, and a link to an ancestor) ends with `loops`. **Validated in the container:** a link to an ancestor resolves to the ancestor's own inode, so identity catches it; but a two-link cycle (A to B to A) makes the kernel answer `ELOOP` ("Too many levels of symbolic links") on every stat and open, so the walk must treat an `ELOOP` on a link as `Unreadable` (a failure recorded in the ledger), not as a loop; a link to the root itself and a link to the root's parent are refused as loops with no second walk of the root; one file reached through two links is one file and a duplicate; a file symlink takes the target's identity; a followed target absent on a later walk keeps its rows. Catalog: `root_volumes` replaced by a complete walk. Library: `lane_volumes` over the union, and `probe_place`'s drive union with a fake `Drives` and `Volumes`. Real links, automated where they need no privilege: a junction needs none on Windows (the platform's `sqlite.rs` makes one with `FSCTL_SET_REPARSE_POINT`; a small helper behind the `testing` feature, in the style of the existing `pg_platform::testing` folders, exposes it to the scan's tests), so a temp-folder test follows a real junction, ends a real loop, and skips a real cloud-tagged entry's classification by tag; a Windows symbolic link needs a privilege, so its test calls `pg_testkit::skip` when it is not held (the repo's pattern for a file system that cannot hard-link); Linux symlinks need none, so the container runs them. By hand: a junction, a symbolic link and a mount folder in a scratch folder pointing at a scratch folder on the F: disk.
